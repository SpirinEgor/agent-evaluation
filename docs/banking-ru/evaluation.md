# Оценка банковской задачи

Справочник по механике оценщиков Banking.ru. Сверено с рабочим деревом
27 октября 2026 года. Нормативные решения находятся в [концепте](../banking-ru.md),
структура критериев — в [формате задачи](task-format.md), компоненты —
в [архитектуре](architecture.md). Ниже отдельно указаны текущий код и пробелы миграции.

## Входы, выходы и граница доступа

Оценщик получает скрытые критерии, эталонные действия, исходный снимок среды
и полную фактическую траекторию. Журнал содержит вызовы, исходные аргументы,
результаты и ошибки, получение результатов и исходящий текст агента.
Один список имён инструментов или заявление агента об успехе недостаточны.

Выход — `RewardInfo`: итог, компоненты и причины несовпадений.
Во время решения агент не получает критерии, эталон или текущую награду.
У Bank 2, Bank 40 и Bank 41 критерии хранятся в `evaluation.json`
каталогов `tasks/bank_002/`, `tasks/bank_040/` и `tasks/bank_041/`;
в остальных 58 задачах — в `evaluation_criteria` внутри `tasks/bank_*.json`.
Загрузчик передаёт оценщику одинаковую модель `Task` независимо от хранения.

В режиме платформы `directory` общий диспетчер преобразует обёртку `bank_call`
в канонические вызовы реальных операций для DB/ACTION. Исходная обёртка
и технические вызовы каталога сохраняются в `mcp_events`; они не заменяют
банковскую траекторию. Общий контроль завершения узнаёт также канонический
`done` из диспетчера. Подробности и отдельные метрики —
в [контракте discovery](discovery.md). Формулы оценки сохранены; у Bank 2/40/41
включён отдельный контракт эквивалентного полного чтения.

## Какие профили сейчас исполняются

Состояние на 28 октября 2026 года, а не постоянное деление набора. Источник
фактического профиля — `evaluation_criteria` каждого файла из индекса задач,
в частности `reward_basis`, `banking_contract_version` и остальные условия профиля.
При миграции обновляй эту таблицу, дату сверки и связанные описания в концепте,
архитектуре, формате задач и README в той же работе. Код может поддерживать
профиль раньше, чем он назначен задаче; новая запись не подтверждает валидацию.

| Задачи | Формула | Механизм |
|---|---|---|
| Bank 2, Bank 40, Bank 41 | DB × ACTION | Явный `db_action_v1`, `full_contract`, бизнес-профиль; ENV assertions и прежний ENV-мост траектории отключены |
| Остальные 58 | DB × ENV_ASSERTION × ACTION | Прежние критерии; удаление ENV требует отдельного переноса уникальных защит |

`reward_basis` определяет участвующие в итоге компоненты. Целевой банковский
контракт — бинарное произведение DB × ACTION; общий движок сохраняет ENV,
COMMUNICATE и NL_ASSERTION для других применений. Наличие этих оценщиков
в движке не означает их участие в банковском балле.

## DB: допустимое конечное состояние

Текущая реализация — [evaluator_env.py](../../src/tau2/evaluator/evaluator_env.py).
Название модуля историческое: он вычисляет DB и поддерживает прежние ENV-проверки.

1. Создаётся свежая среда с исходными данными и начальным состоянием задачи.
2. В ней воспроизводятся фактические действия агента.
3. Отдельно исполняется эталон; объявленные альтернативы дают несколько
   допустимых результатов. Связанные ID берутся через `result_argument_bindings`.
4. Сравниваются семантические хеши состояний. Для DB требуется совпадение
   с одним допустимым вариантом.
5. Для `db_action_v1` дополнительно выполняются объявленные `db_state_checks`.
   Их провал также даёт DB=0.

Банковская нормализация находится в
[BankingTools.get_db_hash](../../src/tau2/domains/banking_ru/tools.py).
Это не побайтовое сравнение всех полей: часть служебной информации исключается
или нормализуется. Бизнес-поля вне хеша требуют явного покрытия.
[db_state_checks.py](../../src/tau2/evaluator/db_state_checks.py) проверяет
заданные поля выбранных конечных записей; само существование нужных записей
не гарантируется универсальной проверкой по пустой выборке.

Неверный конечный остаток, продукт, невыполненная цель или посторонняя запись —
ответственность DB. Эталон строит ожидаемый результат, а не единственный
разрешённый маршрут агента. Проверка должна принимать существенные альтернативы.

## ACTION: необходимые действия и история

Текущая реализация — [evaluator_action.py](../../src/tau2/evaluator/evaluator_action.py).
[trace_evidence.py](../../src/tau2/evaluator/trace_evidence.py) приводит журнал
к наблюдаемым вызовам и результатам. Есть отдельные half-duplex и full-duplex входы.

| Проверка | Текущие декларации и код |
|---|---|
| Необходимые действия и существенные параметры | `actions` с `required_for_reward=true`, сравнение аргументов, объявленные альтернативы и требования успешности |
| Порядок | `action_order`; не навязывает порядок всех независимых действий |
| Полученные основания | `result_evidence`, `argument_evidence`; наличие запроса не равно получению результата |
| Связь результата с аргументом | `result_argument_bindings`, например фактически созданный ID или полученный секрет |
| Авторизация и принадлежность данных | `tool_access_policy`, в том числе discovery клиента и разрешение владельцев объектов |
| Запреты и конфиденциальность | `forbidden_actions`, аргументные и текстовые запреты; общий банковский контракт секретов |
| Предметные процессы | Контракты урегулирования, возвратов, доставки и состояния сверки |

`required_for_reward=false` исключает шаг из самостоятельного списка обязательных
совпадений, но не отменяет отдельный `result_evidence`, требующий его результат.
`compare_args=[]` также не отключает другие проверки доступа и оснований.

Полная ветка проверяет не только подходящую подпоследовательность вызовов:
остальная история может содержать самостоятельное нарушение. Проведённая
запрещённая операция не становится допустимой после отката к правильной DB.
Независимые чтения разрешены параллельно; источник должен быть получен
до формирования зависимого действия, а не просто запрошен раньше.

`presence_and_order` — прежняя ограниченная ветка ACTION. В немигрированных
контрактах дополнительные гарантии могут выполняться через ENV.
Её нельзя считать эквивалентом `full_contract` или менять изолированно от ENV.

## Конфиденциальность и отклонённые запросы

Для Bank 2/40/41 маркер `banking_confidentiality_contract="banking_v1"`
подключает [общие правила](../../src/tau2/evaluator/banking_confidentiality.py)
на основе БД с применённым начальным состоянием. Прямой вызов такого ACTION
без необходимого контекста БД завершается ошибкой оценки и не пропускает защиту.

Проверяется полный исходный журнал: текст, потоковые фрагменты и клиентские
каналы инструментов, включая неудачные вызовы. Входящий клиентский секрет
и разрешённый внутренний `check_otp.code` сами по себе не являются утечкой.
Адресные проверки не доказывают распознавание произвольных кодировок секретов.

В текущем бизнес-профиле часть предметных проверок использует журнал без явно
отклонённых вызовов. Проверки владельцев и разглашения по-прежнему получают
исходную историю. Поэтому исправление формата не гарантирует, что любая
ошибочная попытка будет нейтральной: значение имеют конкретные критерии.

## Что отличается от нового концепта

| Решение концепта | Фактический статус и следующая работа |
|---|---|
| Отклонённый запрос без раскрытия и запрещённого эффекта не снижает балл | Текущий доступ может штрафовать известную чужую цель даже при отказе. Нужна отдельная миграция, без потери контроля фактически раскрытых данных |
| Необходимые актуальные документы получены до зависимых действий | В Bank 2/40/41 file_read, cat и read_document проверяются по снимку корпуса и времени получения; предметную необходимость существующих требований ещё нужно сверять |
| Способ поиска не фиксируется | Не требовать конкретную фразу, просмотр всех страниц или старых редакций; проверять допустимость альтернатив адресно |
| Некорректные вызовы учитываются отдельно | В `directory` диагностируются промахи оболочки и knowledge API, discovery учитывается отдельно; лимит по умолчанию не выбран |
| Каталог и `bank_call` | Реализованы в `directory`; журнал сохраняет реальные операции и исходные аргументы. Единый зачёт cat/read_document/file_read включён явным knowledge_v1 в Bank 2/40/41; остальные задачи сохраняют прежнюю оценку |

Таблица разделяет реализованное поведение и оставшуюся миграцию. Она не разрешает отключать текущую
защиту и не утверждает, что существующие задачи уже проверены по новым правилам.

## Завершение и технический исход

`done` — протокол завершения, а не оценка правильности. `completion_only`
не требует финальной прозы. В бизнес-профиле отсутствие `done` само по себе
не обнуляет достигнутые цели; вне этого профиля действуют прежние проверки
завершения. Технический исход запуска и бизнес-балл нужно рассматривать отдельно.

Отказ проверяемого агента выполнить поручение учитывается как неуспешная попытка;
сбой harness или неподтверждённая изоляция не доказывают предметную ошибку модели.
Исходные события и ограничения проверки сохраняются в отчёте.

## Как проверять изменение оценщика

| Контроль по согласованному концепту | Ожидаемый результат |
|---|---|
| Правильное решение с необходимыми источниками | 1 |
| Существенная допустимая альтернатива | 1 |
| Бездействие или неверный конечный результат | 0 |
| Получены чужие защищённые данные или разглашён секрет | 0 |
| Выполнено запрещённое действие, затем сделан откат | 0 |
| Правильная DB без обязательного актуального источника | 0 и повод проверить качество задачи |
| Исправлена техническая ошибка без предметного нарушения | 1 |
| Отказ в чужих данных без раскрытия или эффекта, затем правильное решение | 1 после миграции соответствующей проверки |

Контроли проверяются целым оценщиком с компонентами и причинами, а не только
прямым вызовом одной функции. Для изменённых общих гарантий учитываются оба
режима траектории. Воспроизведение старых результатов на новой логике не заменяет
исходную оценку: исторические баллы и версии не переписываются.

Точки проверки: [тесты домена](../../tests/test_domains/test_banking_ru/),
[поддерживаемые группы](../../scripts/banking_ru/run_basic_tests.py),
[общие контракты](../../scripts/banking_ru/check_basic_contracts.py).
Выбор команд и разрешённый объём — в [процессе разработки](development.md).
Полная регрессия и модельные попытки из создания этого документа не следуют.

## Эквивалентные операции полного чтения

Контракт и проверка происхождения источников описаны в
[knowledge MCP](knowledge.md#единый-зачёт-полного-чтения-в-action).
Общий evaluate_simulation передаёт ACTION снимок корпуса сценария. Это не
меняет DB и не переписывает исходную траекторию; обе реализации ACTION
используют один адаптер. Поиск и каталог не заменяют полное чтение. Флаг
banking_source_read_contract имеет значение knowledge_v1 только у Bank 2/40/41.
