# Контракт bank_directory и bank_call

Контракт принят и реализован 28 октября 2026 года в выбираемом режиме
платформы `directory`. Режимы `single` и `systems` сохранены для совместимости;
по умолчанию банковский сервис и существующий модельный preflight используют
`systems`. Задачи, критерии и корпус при реализации не изменены.

Реализация: [bank_directory.py](../../src/tau2/platform/bank_directory.py),
[сессия и канонический журнал](../../src/tau2/platform/session.py),
[сервис](../../src/tau2/platform/service.py). Адресно проверены API и транспорт,
эталон/бездействие Bank 2 в двух режимах оценки и представители нарушений;
полная регрессия и модельные прогоны не выполнялись.

Цели и бизнес-правила — в [концепте](../banking-ru.md), компоненты и границы —
в [архитектуре](architecture.md), порядок разработки — в [development.md](development.md).

## Включение режима

```bash
uv run python -m tau2.platform --domain banking_ru --mcp-layout directory
```

Либо передай `mcp_layout="directory"` в `PlatformSettings`, `PlatformSession`
или `PlatformClient.open`. В новой сессии опубликован только общий MCP-эндпоинт
с `bank_directory` и `bank_call`; прямые эндпоинты систем в этом режиме
не публикуются. Маршрутизация использует тот же банковский backend и карту
владельцев операций в одной сессии, что и прежние системные MCP-обработчики.
Внешние сетевые backend-серверы эта работа не подключает.

`--max-discovery-calls N` задаёт явный положительный лимит discovery.
Без флага значение `None`: числовой лимит пока не выбран и автоматически
не назначается. Это не разрешение на модельный запуск; существующий preflight
не переключается на новый режим попутно.

## Вход агента и ответственность платформы

На старте агент получает тикет, минимальный общий `AGENTS.md` и схемы двух
инструментов: `bank_directory` и `bank_call`. Каталоги систем и инструментов,
а также полные схемы банковских операций заранее в контекст не передаются.

Платформа подключает MCP банковских систем и обслуживает адреса, соединения
и служебную авторизацию. Агенту не нужно настраивать токены или угадывать URL.
Один каталог и диспетчер относятся к одной банковской сессии. Открытие схемы
не подтверждает личность клиента и не даёт права читать его данные.

Каталог объясняет, какие системы и операции существуют. Политики и знания
определяют, когда и на каких основаниях их можно применять. Описания API
не содержат готового маршрута решения, списка нужных статей или скрытых критериев.

## Запросы bank_directory

`operation` выбирает действие. Поля в таблице относятся к соответствующей операции;
неприменимые поля не игнорируются молча, а получают понятную диагностическую ошибку.

| operation | Обязательные поля | Необязательные поля | Назначение |
|---|---|---|---|
| `list_systems` | — | `cursor` | Страница банковских систем |
| `search_systems` | `query` | `cursor` | Поиск по ID, названию и назначению системы |
| `list_tools` | `system_id` | `cursor` | Страница инструментов выбранной системы |
| `search_tools` | `query` | `system_id`, `cursor` | Поиск по имени и краткому описанию инструментов; без system_id — по всем системам |
| `open_tool` | `system_id`, `tool_name` | — | Полная входная схема конкретного инструмента |

`system_id`, `tool_name` и `query` — строки; `cursor` — непрозрачная строка
из предыдущего ответа. Для первой страницы cursor не передаётся. У list/search
фиксированный размер страницы: до пяти записей, параметров `limit` и `page_size` нет.

### Ответы просмотра и поиска

Общая форма: `items` и `next_cursor`. Последняя страница содержит
`"next_cursor": null`; пустой результат — `"items": []` и `"next_cursor": null`.
Пустой поиск не является некорректным вызовом.

Карточка системы содержит только `system_id`, `name`, `description`.
Карточка инструмента — `system_id`, `tool_name`, `description`.
В карточках нет аргументов, схем результата, списка ошибок или готового процесса.
`system_id` в выдаче инструментов нужен в том числе для поиска по всем системам.

### Порядок, поиск и курсоры

- Каталог фиксируется на время сессии. Порядок систем стабилен по `system_id`,
  инструментов — по `system_id` и `tool_name`.
- Поиск детерминированный по указанным полям каталога; нормализуются регистр,
  пробелы и `ё/е`. Все слова нормализованного запроса должны встречаться
  как подстроки в полях карточки; морфология и синонимы не достраиваются.
  Модельное ранжирование в первой версии не применяется.
- Выдача не зависит от тикета, эталона, скрытых критериев или успешных траекторий.
- Курсор связан с операцией, запросом, фильтром системы и снимком каталога сессии.
  В следующем запросе сохраняются операция и фильтры. Курсор нельзя применять
  к другому запросу; некорректный курсор даёт `INVALID_CURSOR`.
  Подпись использует отдельный случайный ключ сессии, не публичный токен из URL.
- Непрозрачный курсор в примерах — иллюстрация: агент передаёт фактически
  полученное значение, а не вычисляет номер страницы.

Для нынешних 13 систем полный просмотр даст страницы 5 → 5 → 3. Это описание
текущей карты, а не постоянное ограничение числа систем.

### 4. Открытие входной схемы

```json
{
  "operation": "open_tool",
  "system_id": "crm",
  "tool_name": "find_customer"
}
```

```json
{
  "system_id": "crm",
  "tool_name": "find_customer",
  "description": "Найти клиентские записи по телефону, фамилии и дате рождения.",
  "input_schema": {
    "type": "object",
    "properties": {
      "phone": {
        "type": ["string", "null"],
        "default": null,
        "description": "Номер телефона клиента."
      },
      "last_name": {
        "type": ["string", "null"],
        "default": null,
        "description": "Фамилия клиента."
      },
      "birth_date": {
        "type": ["string", "null"],
        "default": null,
        "description": "Дата рождения в формате ГГГГ-ММ-ДД."
      }
    },
    "required": [],
    "additionalProperties": false
  }
}
```

У нынешнего `find_customer` все три аргумента опциональны в сигнатуре;
у других операций обязательные поля перечисляются в `required`.
Схема описывает назначение, аргументы, типы и обязательность. Схему ответа,
перечень ошибок и порядок бизнес-процесса в ответ `open_tool` не включаем.

Открытая схема сохраняется до конца сессии; повторное открытие возвращает
ту же схему. Ответ открытия должен быть передан до формирования зависимого
`bank_call`: получение схемы между формированием и исполнением вызова не считается
основанием. Повторное открытие не отменяет уже полученную схему. Для открытия не требуется предварительно пролистать каталог:
если агент получил корректные идентификаторы из доступного контекста,
он может обратиться к `open_tool` напрямую.

## Контракт bank_call

Запрос содержит `system_id`, `tool_name`, `arguments`. Система и инструмент
задаются строками; `arguments` — объект переданных аргументов.

Пример вызова после открытия схемы, с условным номером из тикета:

```json
{
  "system_id": "crm",
  "tool_name": "find_customer",
  "arguments": {
    "phone": "+7 900 000-00-00"
  }
}
```

Платформа проверяет систему, инструмент, факт открытия его схемы и аргументы,
затем направляет вызов соответствующему MCP текущей сессии. Агент получает
фактический результат операции, а не синтетический бизнес-ответ диспетчера.
Скрытие схемы результата не означает скрытие фактических данных после вызова.

У `bank_call.arguments` нет закрытого списка полей: оболочка должна пропускать
придуманные аргументы и неверные типы значений до серверной проверки. Входная
схема конкретной операции при этом может содержать `additionalProperties: false`.
Это описание допустимых аргументов операции, а не запрет передать ошибочный
объект диспетчеру. Клиентская валидация или enum всех инструментов в оболочке
не должны делать такие промахи ненаблюдаемыми.

Если вызов не соответствует входной схеме, он целиком отклоняется до исполнения:
лишние поля не отбрасываются, неверные значения не приводятся молча к нужному типу.
Агент получает понятную ошибку; исходные аргументы и причина сохраняются в журнале.

## Ошибки, журнал и оценка

| Событие | Поведение |
|---|---|
| Нет совпадений в поиске | Пустая страница; нормальный результат |
| Неизвестная система или инструмент | Понятная ошибка; банковская операция не исполняется |
| Схема не открыта | `TOOL_SCHEMA_NOT_OPENED`; банковская операция не исполняется |
| Лишнее поле, неверный тип или пропущенный обязательный аргумент | Весь вызов отклоняется до исполнения; понятная ошибка и отдельная диагностика |
| Повторное открытие схемы | Та же схема; открытое состояние сохраняется |
| Ошибка самой банковской операции | Возвращается фактическая ошибка MCP; последствия проверяются по состоянию и журналу |

Журнал сохраняет реальную систему, операцию, исходные аргументы, результаты,
ошибки и временные границы запросов и получения ответов. В `mcp_events` остаётся
исходный `bank_call` вместе с `canonical_name` и `canonical_arguments`.
Траектория оценщика содержит реальные операции; вызовы каталога остаются
в техническом журнале и не воспроизводятся как банковские действия.
`done` вызывается через открытый `support/done`; общий оценщик распознаёт
его каноническое имя и в прежних профилях `completion_only`.

Старые `unlock_discoverable_agent_tool` и `call_discoverable_agent_tool`
в новом каталоге отсутствуют, чтобы не обходить открытие схемы общего диспетчера.
Они сохранены в прежних режимах. `give_discoverable_user_tool` остаётся операцией
клиентского канала и не исполняет произвольные агентские инструменты.

Технические промахи учитываются отдельно от бизнес-балла. После корректного
восстановления они сами по себе не обнуляют DB × ACTION. Фактическое получение
чужих защищённых данных, разглашение или исполненное запрещённое действие
оцениваются по бизнес-контракту; каталог не меняет правила доступа.

## Бюджеты и оставшаяся детализация

Все операции `bank_directory`, включая отклонённые запросы, поиск и открытие
схем, относятся к discovery. Счётчик ведётся отдельно. При превышении явно
заданного лимита каталог возвращает `DISCOVERY_BUDGET_EXHAUSTED`; уже открытые
операции и завершение остаются доступны через `bank_call`.

В банковский бюджет входят вызовы операций и отклонённые попытки исполнения;
успешный `done` не расходует этот бюджет. Самостоятельные обращения к прежним
именам на общем интерфейсе отклоняются как неправильные вызовы. Сохраняются
100 банковских вызовов и `max_errors=0` по умолчанию. Ошибки оболочки/схем
не включаются в счётчик остановки по ошибкам; ошибки исполненного backend
сохраняют прежний учёт отдельно.

В состоянии и результате сессии нового режима поле `discovery` содержит `calls`,
`max_calls` и `tool_call_errors` — количества диагностик по коду. Полные события
с `call_id`, именем интерфейса и кодом также сохраняются в записи симуляции.
Коды оболочки: `INVALID_ARGUMENT`, `UNKNOWN_SYSTEM`, `UNKNOWN_TOOL`,
`INVALID_CURSOR`, `WRONG_SYSTEM`, `TOOL_SCHEMA_NOT_OPENED`,
`DISCOVERY_BUDGET_EXHAUSTED`. Ответ MCP имеет `isError` и понятный текст;
счётчики не подменяют бизнес-балл.

Распределение knowledge-операций и команд по бюджетам реализовано в `directory`
и описано в [контракте knowledge MCP](knowledge.md). Миграция метаданных корпуса
и проверки чтения остаётся отдельным этапом. Нужно выбрать лимит discovery и переключить модельный
preflight с проверкой его границы доступа. Это отдельная работа; новая реализация не подтверждает
валидность всех задач и не разрешает модельные прогоны или миграцию критериев.
