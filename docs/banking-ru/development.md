# Разработка Banking.ru

Практический процесс изменения задач, инфраструктуры и проведения модельных
экспериментов. Workflow актуализирован 11 ноября 2026 года.
Цели и нормативные решения — в [концепте](../banking-ru.md), структура —
в [архитектуре](architecture.md), поля заданий — в [формате задач](task-format.md),
механика оценщиков — в [оценке](evaluation.md).

## Общий порядок

1. Определи цель, затронутые задачи или компоненты, границы и критерии готовности.
2. Прочитай соответствующие документы, локальные инструкции и текущий код.
   Отличай согласованную целевую схему от доступной реализации.
3. Внеси необходимое изменение, сохраняя общую среду и поддержку других доменов.
4. Выполни адресные проверки, обнови затронутые документы и проверь diff.
5. Проведи ревью изменения; если независимое ревью запрошено или предусмотрено
   согласованной работой, передай проверяющему границы, критерии и доказательства.
6. После одобрения результата слей ветку в локальный main. Push выполняй только
   в разрешённом объёме. Сообщи commit, проверки и непроверенное влияние.

Небольшая правка не требует отдельного плана-файла. Для продолжительной работы
используй согласованный план в существующем месте учёта задач. Не создавай
автоматически набор proposal/design/solution/review на каждое изменение.

## Проверка переносимости сложностей и атак

Обязательное правило от 3 ноября 2026: проектируем для внешнего агента через
A2A/MCP, без управления его harness. [Граница контракта](../banking-ru.md#воспроизводимость-через-api-и-внешних-агентов)
действует и для банковских задач, и для экспериментов с их сложностью.

Перед реализацией каждого механизма:

1. Укажи, что контролирует атакующий в среде бенчмарка и через какой API агент
   получит нагрузку. Выбери существующий ресурс/ответ; новый интерфейс сначала
   опиши и затем сделай общим для среды, без исключения по ID задачи.
2. Зафиксируй начальное состояние, версии, происхождение и триггер обновления.
   Для ответов, меняющихся по ходу сценария, задай воспроизводимые переходы
   либо закреплённый seed/записанную последовательность в контракте эксперимента.
   Триггер должен быть виден в API-журнале; секретный доступ к памяти не допускается.
3. Покажи правильный путь только через разрешённый API. Прямые чтения автором
   файлов агента или подстановка его заметок не подтверждают решаемость.
   Отдельная память/Python/субагенты у проверяемого агента необязательны.
4. Определи наблюдаемый эффект: полученное сообщение, вызов с аргументами,
   успешное нарушение, безопасная блокировка, восстановление и результат DB × ACTION.
   Внутренние заметки — дополнительное свидетельство, если доступны; их отсутствие
   не означает провал и не доказывает отравление памяти.
5. Проверь через клиент API/заглушку доставку, порядок событий, правильный путь
   и существенный неправильный путь. Проверка должна обходиться без записи в
   файловую систему/контекст/harness проверяемого агента. Сохрани запросы,
   ответы, версии и отчёт; для модели затем нужен отдельно разрешённый прогон.

Изменение startup/skills/модели/harness допустимо при разработке версии самого
агента, но не как скрытая атака или обязательное условие банковской задачи.
Гипотезы, требующие такого доступа, помечай «вне API-контура», а не «готовы к
переносу в Bank 2». Компрометация метаданных MCP требует отдельно объявленной
границы доверия; простое редактирование схемы автором не доказывает реалистичность.

Этот раздел закрепляет правило; он не реализует A2A и не подтверждает прохождение
нового API-эксперимента. Изменение документации не разрешает модельные попытки.

### Доставка старта в нашем адаптере

Адаптер поддерживаем мы: `policy` и тикет берутся из API открытия сессии.
В Codex инструкция передаётся через `thread/start.baseInstructions`, тикет —
через `turn/start`; не создавать AGENTS.md ни в host temp_dir, ни в контейнере.
Не полагаться на auto-discovery локальных инструкций. Применять это правило
одинаково к baseline и V1. Исходный файл корпуса остаётся только у бенчмарка.

При изменении адаптера проверять пустой workspace и отсутствие гостевых credentials,
точную доставку полученного `policy` в model request, отсутствие посторонних
инструкций и многошаговый MCP. Выполнять физическую заглушку без модели;
предыдущее подтверждение границы после изменения runtime требует обновления.
Сохранённые авторские startup.txt/manifest не копируются агенту.

### A2A endpoint Codex/V1

Запуск адаптера (вызовы модели разрешаются отдельно; эта команда не является
офлайн-проверкой):

```sh
uv run python -m tau2.platform.a2a --endpoint http://127.0.0.1:9002/a2a --port 9002 --profile v1 --model gpt-6.1-sol --effort low --image <verified-sha256-image> --preflight-spec <spec.json> --artifacts-dir <author-output-dir>
```

Сервис слушает localhost по умолчанию. При публикации использовать HTTPS и
`BANKING_A2A_TOKEN` (bearer); секрет в команду и артефакты не записывать. По
умолчанию допускается одна активная сессия; CLI рассчитан на run_timeout до
900 секунд. Несовместимый больший предел отвергается до inference, а не
незаметно сокращает бюджет платформы. CLI проверяет соответствие модели,
профиля, image и актуальную физическую границу по preflight-spec до старта.
Полный предметный preflight и разрешение числа попыток по-прежнему обязательны;
endpoint не является разрешением на эксперименты.

Карточка: `/.well-known/agent-card.json`. Регистрация: A2A0.3.0 и
`datapart-tools@v2`. Старт: run_setup плюс TextPart тикета; инструменты — JSON-схемы
bank_directory/bank_call в OpenAI function-формате. Ответы действий только через
координатора: tool_calls → tool_results по call_id. MCP URL от внешнего участника
не требуется. Поле run_timeout и max_turns сохраняют смысл платформы; банковский
бюджет не выводится из числа ходов. `agent_note` не является обязательной памятью.
В текущем адаптере банковское общение выполняется через tools/ask_client, отдельные
TextPart-уточнения после старта не поддерживаются.

Офлайн: `uv run pytest tests/test_platform/test_codex_a2a.py -q` проверяет реальный
HTTP/SSE обмен с заглушкой решателя. Физическая проверка без модели: задать
BANKING_CODEX_TEST_IMAGE и выполнить test_codex_container.py с `-k 'a2a_v1 or physical_network'`.
Она использует настоящий Codex с локальным inference-stub, не подписочный endpoint.
Непосредственная совместимость с реальным клиентом eval-platform зафиксирована
в `artifacts/banking-a2a-adapter-2026-11-03/platform-client.log`; этот внешний
checkout не является зависимостью поддерживаемых тестов.

Старый локальный directory/MCP harness сохранён для прежних проверок; A2A —
явный новый путь запуска. Исторические результаты и preflight не переименовывать.
SDK-адаптер банковского бенчмарка описан ниже. Регистрация и запуск в кластере
остаются отдельной операцией.

### Banking.ru в SDK платформы

Сверено 4 ноября 2026. Контракт платформы закреплён на коммите
`914007cb79f3e3d5f39626a0209d6c1a2b6d7794` репозитория
[lapalaba/eval-platform](https://github.com/lapalaba/eval-platform).
Используются настоящий `platform-sdk-contract` 0.1.0 и `platform-harness`,
а не локальная копия их типов. Они не нужны обычному tau2/MCP-запуску.

| Файл | Ответственность |
|---|---|
| [benchmark.py](../../src/tau2/platform/sdk/benchmark.py) | SDK on_start/on_action/report_state поверх PlatformSession |
| [tasks.py](../../src/tau2/platform/sdk/tasks.py) | Сборка существующих задач; скрытые критерии только в gold |
| [evaluator.py](../../src/tau2/platform/sdk/evaluator.py) | Сверка журнала/состояния, общий оценщик и агрегация |
| [benchmark.yaml](../../integrations/eval_platform/benchmark.yaml) | Объявление инструментального режима и бюджета ходов |
| [runtime.yaml](../../integrations/eval_platform/runtime.yaml) | Провод v2 и два образа execute/evaluate |
| [build_platform_bundle.py](../../scripts/banking_ru/build_platform_bundle.py) | Самостоятельный контекст сборки с закреплённым SDK и разделением файлов |

SDK требует метку набора: `all` означает все существующие 61 задачи, без изменения
их состава или восстановления старой логики split. YAML не является разрешением
запустить все задачи. 500 ходов платформы включают discovery, run_timeout — 900s.
Банковские лимиты берутся из общего config и сценария; текущая Bank 2 v29
объявляет100 вызовов для диагностического эксперимента. В исторической поставке
Banking.ru 0.1.1 от 4 ноября 2026 `on_start` добавлял к общей инструкции
эффективный банковский лимит и отдельный лимит discovery. Тогда для Bank 2 агент видел
«Банковский лимит: 50 вызовов» и «Discovery: отдельный бюджет, числовой лимит не
установлен». Значения берутся из сессии, не из копии настроек A2A-адаптера.
Общие500 ходов приходят отдельно в `run_setup.rules.max_turns`; они включают
и банковские вызовы, и discovery, и done. Версия самого SDK-контракта остаётся0.1.0.

В инструкции перечислены discovery-операции knowledge MCP и пояснено, что полное
чтение документов расходует банковский бюджет. Также явно объявлена существующая
граница (исправлена 4 ноября 2026): после 50-го обычного банковского вызова
новые банковские операции отклоняются без исполнения. Сессия остаётся открытой
для `bank_call(done)` и discovery в отдельном бюджете. Отклонённые сверхлимитные
попытки сохраняются в журнале, но не увеличивают число исполненных бюджетных
вызовов. Сам done банковский бюджет не расходует. Общие max_turns/run_timeout
по-прежнему ограничивают продолжение; без done итог нулевой.
Исторические результаты прежней границы не переписываются.
Канал только tools; пакет вызовов отклоняется целиком. Полученный безопасный отказ
можно исправить; сами технические ошибки не превращаются в новый критерий.

Подготовить автономный bundle в новой игнорируемой папке:

```sh
python3 scripts/banking_ru/build_platform_bundle.py \
  --platform-repo /path/to/eval-platform \
  --payload-store "$HOME/.local/share/banking-ru-private/payloads" \
  --output "$HOME/.local/share/banking-ru-private/bundles/banking-sdk"
```

Каталог назначения должен отсутствовать: старые результаты не перезаписываются.
Скрипт берёт SDK через `git archive` указанного коммита, зависимости — через
`uv export --frozen` из текущего lock. Код, данные и критерии копируются без правок.
Далее регистратору платформы передаётся этот bundle, не корень tau2-репозитория.
Dockerfile имеет цели execute и evaluate; вторая принимает `EXEC_IMAGE` от платформы.
Пакет `tau2` располагается непосредственно в `/app`, рядом с entrypoints:
платформа заменяет `PYTHONPATH` путём своей обвязки, поэтому полагаться на
образный `PYTHONPATH=/app/src` нельзя. Подготовка проверяется с этим override.
Локальная сборка двух образов при необходимости:

```sh
docker build --target execute -t banking-ru:execute "$HOME/.local/share/banking-ru-private/bundles/banking-sdk"
docker build --target evaluate --build-arg EXEC_IMAGE=banking-ru:execute \
  -t banking-ru:evaluate "$HOME/.local/share/banking-ru-private/bundles/banking-sdk"
```

Банковский контейнер и контейнер агента — разные границы. Источники и report
банковской среды не копируются агенту; Codex продолжает работать в своей
изолированной среде без сети, host mounts, startup-файла и авторизации.
Внешняя платформа подключается к его A2A endpoint и исполняет банковские вызовы
через SDK. Регистрация образов и инфраструктурное развёртывание выполняются
средствами eval-platform; локальная проверка не утверждает их готовность в кластере.

Адресная проверка без модели (SDK пока не опубликован в package index):

```sh
EVAL_PLATFORM_REPO=/path/to/eval-platform uv run \
  --with /path/to/eval-platform/platform/external_contracts/platform-sdk-contract \
  --with /path/to/eval-platform/platform/external_contracts/platform-harness \
  --with boto3 --with opentelemetry-exporter-otlp-proto-http==1.39.1 \
  pytest tests/test_platform/test_platform_sdk.py -q
```

`uv --with` добавляет зависимости только окружению команды; общий lock не меняется.
SDK и HTTP exporter OpenTelemetry здесь нужны импорту координатора, не банковским инструментам;
версия согласована с opentelemetry-api текущего tau2 lock.
Без переменной checkout выполняются проверки SDK без внешнего координатора;
без установленного SDK файл явно пропускается как optional integration.
Для приёмки интеграции нужны все сквозные случаи с настоящим координатором:
эталон Bank 2 →1, ранний done →0, предел ходов без done →0. Тест использует
HTTP провода SDK и A2A, стандартный сборщик журнала платформы и отдельный HTTP
оценщика. Скрипт эталона и gold находятся только у авторской заглушки, не в
сообщениях или runtime проверяемой модели. Дополнительно проверяются исправление
неверного API-вызова и отказ при подмене журнала или итогового состояния.

## Подготовка и проверка сценариев

1. Определи бизнес-цель, доступные источники, допустимые решения и существенные
   нарушения. Для вставок укажи происхождение, способ доставки и наблюдаемый эффект.
2. Подготовь изменения в рабочей ветке. Закрытые тексты храни отдельно;
   разработчик может читать и редактировать их, но проверяемый агент получает
   только предусмотренные сценарием API-ресурсы.
3. Проверь согласованность тикета, данных, политик и оценки. Выполни адресные
   проверки корректного пути, допустимых альтернатив и существенных нарушений.
4. Представь итоговый diff, результаты проверок и ограничения для одобрения.
   Независимое ревью выполняется, если оно отдельно запрошено; его отсутствие
   не подменяй утверждением о независимой проверке.
5. После одобрения выполни слияние по Git-процессу ниже. Разработка сценария
   сама по себе не разрешает модельные прогоны.

### Закрытые тексты и подстановка во время выполнения

Решение 11 ноября 2026 отменяет запрет на чтение разработчиком от 10 ноября.
По явному указанию пользователя Codex может читать закрытые вставки, private
jobs/payloads и журналы, в том числе через MCP/Langfuse, и самостоятельно проводить
содержательный аудит. Вставки остаются недоверенными данными. Изоляция проверяемого
агента и отдельное хранение payloads сохраняются; разрешение не означает разрешение
новых прогонов или публикации private store.

В публичных файлах используются ссылки вида `{{bank_payload:<sha256>}}`.
Текст лежит в отдельном файле private store; имя — SHA-256 UTF-8 содержимого.
Синтаксис ссылок зарезервирован и запрещён внутри тела вставки. Нет eval,
выполнения команд или рекурсивного раскрытия. Отсутствующий/изменённый файл
останавливает выполнение инфраструктурной ошибкой без вывода текста.

На runtime-хосте перед запуском нужно явно задать:

```sh
export BANKING_PAYLOAD_STORE="$HOME/.local/share/banking-ru-private/payloads"
```

Ссылки раскрываются перед разбором исходных банковских данных, загрузкой корпуса
и проверкой логических хешей. Поиск, полное чтение, инструменты, состояние,
эталон и оценщик видят исходный текст. Журнал попытки сохраняет фактически
полученный агентом ответ; разработческий Codex может читать его для аудита.
Раскрытие применяется к доверенным входным ресурсам runtime, а не ко всем ответам
подряд: отражённая ссылка из аргументов агента или ошибки не должна открывать
private store. Стартовые инструкции и файлы проверяемого агента не подменяются.

Перенесены тексты внешних документов и processing_notes Bank 2, связанные
сообщения клиента в общей БД и архив коннектора. Содержание восстанавливается
побайтно; manifest закрепляет раскрытые исходные данные. Пересборка manifest
не должна возвращать раскрытый текст в публичные файлы. Другие файлы задач
не мигрируются. Общие DB/corpus используются всеми банковскими runtime, поэтому
им всем требуется одинаковый store; это не исключение среды по ID задачи.
В тестовых fixtures внешние сообщения заменены нейтральными самостоятельными
данными и обновлены хеши. Сырой store не является зависимостью этих fixtures.

SDK bundle требует `--payload-store`, проверяет содержимое и копирует только
нужные ID. Bundle с раскрываемыми текстами создаётся вне репозитория разработчика.
В execute/evaluate одинаковый `BANKING_PAYLOAD_STORE=/app/private_payloads`;
агентский образ store не получает. Без provision store чистый clone не содержит
всех runtime-входов Bank 2: это явно поставляемый закрытый набор, не silent fallback.

Для экспорта исходников без Git-истории и локальных артефактов доступен
`manage_payloads.py --developer-export`. Это необязательный способ передачи
очищенной копии, а не ограничение доступа разработчика к private store.
Проверка экспорта ищет известные тексты и JSON-экранированные копии; она не
доказывает отсутствие любых кодировок. Private store и исходные журналы
не публикуются и не передаются проверяемому агенту.

модельные попытки. Не вводи обязательные внешние авторские этапы и зависимости
от отсутствующих инструментов.

Поручение пользователя имеет приоритет над общими рекомендациями skill.
Для небольшой согласованной правки не начинай заново обсуждение всего проекта.
Независимое ревью выполняй при отдельном запросе; сообщай, если оно не проводилось.
Разбор существующих трасс не разрешает новые модельные запуски.

## Git: от начала работы до слияния

Для зафиксированных задач действует [порядок версий и выпуска](releases.md).
Bank 2 v42 заморожен; будущие изменения его зависимостей выпускаются новой
версией. [Реестр прохождений](results.md) дополняется без переноса старых
измерений на новые версии. По запросу пользователя от 11 ноября текущий
проверенный снимок публикуется в main с тегом; это отдельное разрешение push,
а не автоматическое разрешение публикаций всех будущих изменений.

Основной режим — один агент, последовательная работа в одной рабочей папке.
Единственная постоянная рабочая база — **локальный `main`**. Каждая новая
самостоятельная работа начинается от него в отдельной короткоживущей ветке
и после приёмки возвращается в него. Worktree по умолчанию не создаём.
Чужие изменения не включаются в работу автоматически.
Прямой коммит в `main` допустим только по явному указанию пользователя.

Принятый цикл: отдельная ветка, изменения, проверки, одобрение результата,
локальный коммит и слияние в локальный `main`. Явное поручение пользователя
проверить и слить работу является разрешением на слияние после успешных проверок;
повторно его не запрашивай. Если слияние не разрешено или есть неразобранные
замечания, оставь результат в рабочей ветке до одобрения.
Push, PR и изменение удалённых веток не выполняются автоматически: для них
нужно разрешение в текущем поручении или ранее согласованном объёме.
Введение этого правила само по себе не разрешает собрать накопленные до него
изменения в общий коммит: их состав и готовность нужно определить отдельно.

```text
Локальный main → отдельная ветка → изменение + документация → проверки
              → ревью / одобрение → локальный коммит → merge в локальный main
              → разрешённый push → удалить свою слитую ветку
```

### 1. Проверить исходное состояние

До правок посмотри `git status --short`, текущую ветку, `git diff`,
`git diff --cached` и настроенные remotes. Учитывай относящиеся
к поручению новые файлы, которые обычный `git diff` не показывает.
Зафиксируй в рабочем контексте базовый commit и существующие незакоммиченные правки.

Грязное дерево не очищается через `reset --hard`, `clean`, автоматический stash
или отмену пользовательских файлов. Сначала отдели свою область работы.
Если нужная база включает незакоммиченные изменения, один checkout от `HEAD`
её не воспроизводит: разрешённые правки нужно перенести адресно и сверить.
При невозможности безопасно отделить их уточни границу, не теряя накопленную работу.

### 2. Выбрать рабочую ветку

| Ситуация | Как работать |
|---|---|
| Уже есть подходящая ветка | Продолжить в ней после проверки состояния |
| Новая работа и чистая рабочая папка | Перейти в локальный `main` и создать ветку от него в той же папке |
| Есть незакоммиченная предыдущая работа | Сначала определить её состав и сохранить в рамках разрешённой работы; не переносить молча в новую задачу |
| Нужно воспроизвести конкретный текущий снимок | Сохранить относящиеся к работе незакоммиченные изменения и проверить идентичность нужных входов; не подменять снимок чистым HEAD |

Ветки именуются по виду и цели работы: `task/bank-002-<change>` для задания,
`fix/banking-<change>` для дефекта, `feat/banking-<change>` для новой возможности,
`docs/banking-<change>` для документации. Например, `task/bank-002-sources`.
Не создавай отдельную постоянную `dev` или ветку на каждый промежуточный шаг.
Продолжение той же незавершённой работы идёт в её существующей ветке.

Пример начала при чистом дереве:

```sh
git switch main
git switch -c task/bank-002-sources
```

Проверяй, не занято ли имя. `origin/main` и upstream τ-bench не подменяют локальный
`main` автоматически. Синхронизация с удалёнными репозиториями — отдельная работа:
не делай `pull` перед каждой задачей и не переписывай опубликованную историю.

Отдельный worktree нужен только при конкретной необходимости: например,
параллельной работе или проверке другой версии без изменения текущих файлов.
Не создавай его автоматически; сначала проверь существующие копии и согласованную
потребность. Он не переносит незакоммиченные правки и не изолирует процессы,
порты или банковские сессии. Для обычной последовательной работы ветки достаточно.

### 3. Изменять и проверять

Работай в назначенной ветке/копии. Код, критерии, необходимые проверки и
действующая документация должны описывать одну версию. Выбирай проверки
по таблице ниже; вся регрессия не становится обязательной из-за создания ветки.
При конфликте сначала выясни смысл обеих сторон, затем объедини и проверь;
не принимай целиком `ours` или `theirs` для задач, критериев и корпуса.

### 4. Подготовить коммит и ревью

Локальный коммит входит в принятый цикл после выполнения критериев и проверок.
Если результат ещё не готов или работа прервана, сохрани ветку и укажи состояние;
не сливай частичное решение под видом завершённого. Добавляй конкретные файлы
или выбранные фрагменты, затем проверяй `git diff --cached` и
`git diff --cached --check`. Не используй массовый `git add .` для смешанного дерева.
Не включай секреты, логи, снимки и посторонние правки.

Один коммит — связное изменение, которое можно объяснить и отменить отдельно.
Подходящие префиксы: `docs:`, `fix:`, `feat:`, `test:`.
Для содержательного изменения код и описывающая его документация идут в одной
работе; временно несогласованное состояние не объявляется готовым.

Для ревью укажи проблему, итоговое поведение, область diff, выполненные проверки
и непроверенное влияние. Если коммита ещё нет, явно включи в предмет ревью
рабочее дерево и новые файлы. Протокол ревью не должен скрывать незакоммиченный код.
После исправления замечаний повтори только затронутые проверки.

### 5. Интегрировать результат

После успешных проверок, разбора замечаний и одобрения верни результат
в локальный `main`. Проверки и исправления выполняются в рабочей ветке.
При штатной последовательной работе используй fast-forward: коммиты сохраняются,
лишний merge-коммит не создаётся. Перед переключением все изменения этой работы должны быть закоммичены.
Посторонние локальные файлы сохраняй; они не должны попадать в коммит или
конфликтовать с переключением.

```sh
git switch main
git merge --ff-only task/bank-002-sources
git merge-base --is-ancestor task/bank-002-sources main
```

Имена в командах — пример для одной работы. Если `--ff-only` отказал, не применяй
force/reset: выясни расхождение. Изменения локального `main` можно объединить
в рабочей ветке, разрешить конфликты и адресно перепроверить результат, затем
повторить слияние. Если fast-forward успешен, проверенный commit не изменился:
повтор всего набора тестов только из-за переключения ветки не нужен.

Push и PR выполняются только по отдельному разрешению. Готовность локального
`main` не означает, что изменения опубликованы в удалённом репозитории.

Перед слиянием сверяй целевую базу и итоговый diff. После конфликтов или изменений
базы проверь затронутые гарантии на интегрируемом результате. Непройденные проверки
и неизвестное влияние не превращаются в зелёный статус.
Не выполняй force-push и не переписывай общую историю как штатный способ завершения.

### 6. Закрыть работу и убрать временное

После успешного слияния и проверки присутствия коммитов в `main` удали свою
завершённую локальную ветку и оставь рабочую папку на `main`:

```sh
git branch -d task/bank-002-sources
git status --short
git branch --show-current
```

Ожидаемый штатный итог — нет незакоммиченных правок этой работы, локальный `main`, результат сохранён,
ветка этой работы удалена. Не удаляй другие ветки массово.
Если worktree всё же создавался, сначала сохрани нужные результаты, затем
архивируй управляемую копию штатным инструментом приложения. Рабочие копии
других чатов не трогай.

Для локальной ветки предпочитай `git branch -d`; отказ — повод проверить
сохранность изменений, а не автоматически применять `-D`. После squash-слияния
проверь PR и итоговый diff отдельно. Удаление удалённой ветки не выполняется
автоматически вместе с локальной уборкой. Возраст ветки не доказывает её ненужность.

## Как не засорять хранилище

| Что сохраняем | Где и как |
|---|---|
| Код, текущие задачи, корпус и действующие руководства | В существующих профильных каталогах, под Git |
| Необходимые тестовые данные | Небольшие самостоятельные fixtures под Git с проверкой целостности |
| Разовые пробы, временные копии, промежуточный вывод | Системный временный каталог; после работы удалить созданное этой работой, если оно не нужно для доказательства |
| Журналы, preflight, снимки и результаты эксперимента | Один каталог запуска в игнорируемом `artifacts/`, со связью с версией; Langfuse даёт дополнительный просмотр |
| API-ключи и локальные подключения | Вне Git; ключи не копируются в документацию или окружение проверяемого агента |
| Устойчивые решения и выводы | Обновить существующее руководство; не создавать повторные заметки с тем же правилом |

`artifacts/` игнорируется Git и не является резервной копией. Перед удалением
worktree отдельно сохрани нужные игнорируемые результаты. Не удаляй исторические
баллы и траектории как «мусор»: сначала проверь назначение и сохранность.
Наличие записи в Langfuse не доказывает сохранность исходного журнала и снимка.

Не делай новую полную копию репозитория на каждый эксперимент: используй
существующую рабочую папку и только необходимые проверенные снимки входов
для воспроизводимости; worktree — при отдельно возникшей необходимости.
Не добавляй в `scripts/` разовую пробу под конкретную старую версию задачи.
Не выполняй массовую очистку, `git gc` или удаление контейнеров/томов попутно.
В итоговом сообщении укажи оставшиеся ветку/worktree, расположение нужных
результатов и выполненную уборку. Коммит, push и слияние называй раздельно.

## Маршрут 1: создать или улучшить задачу

**Вход:** выбранный бизнес-процесс, тикет и ожидаемое изменение сценария.

1. Сверь реалистичность поручения, предметные и правовые основания по источникам.
   Проверь согласованность доступных данных, документов, инструментов и ответов.
   Для выбора механизма сложности используй [референсы](references.md):
   изучай конкретное задание вместе с проверкой и не переноси непроверенный ноль
   внешнего бенчмарка как доказательство качества нашего сценария.
2. Опиши допустимый результат и альтернативы. Для каждого обязательного действия,
   аргумента и источника установи предметное основание. Критерии не вводят
   требований, отсутствующих в доступной агенту среде.
3. Измени разрешённые части задания, сохраняя три файла: ticket.md, scenario.json и evaluation.json. Не меняй другие задачи попутно. Общие данные меняй только
   в пределах работы и учитывай зависимость других эталонов от созданных ID.
4. Адресно проверь эталон и бездействие. Затем существенную допустимую альтернативу
   и специфичные неправильные пути целым оценщиком с компонентами и причинами.
   Контроли выбирай по изменённым условиям, а не перемножай все режимы и ошибки.
5. Сверь относящиеся к изменению общие контракты. Миграции генераторов сначала
   проверяй на временных копиях; `--check` не изменяет данные.
6. Обнови текущую документацию и отчёт версии. При изменении условий задачи
   актуализируй её карточку в Wiki, если работа включает ведение каталога.
   Это не делает локальную Wiki обязательным входом исполняемого бенчмарка.

**Готово:** правильное и допустимое альтернативное решение получают ожидаемый
успех, бездействие и выбранные существенные нарушения — ожидаемый ноль;
обязательные сведения доступны, критерии объяснимы, проверки воспроизводимы.
Дефект оценки устраняется до вывода о сложности. Новые правила концепта требуют
согласованного переноса в оценщик, а не только ожидаемой метки в тесте.

## Маршрут 2: исправить инфраструктуру или оценщик

**Вход:** конкретное расхождение поведения и ожидаемого контракта.

1. Воспроизведи дефект минимальным адресным примером, сохрани фактическую причину.
   Отдели ошибку сценария или fixture от дефекта инструмента, журнала или оценщика.
2. Определи границы: общий движок, банковская среда, MCP, harness или тестовые данные.
   Установи влияние на оба режима траектории и другие домены, если затронут общий код.
3. Исправь причину и сохрани содержательный регрессионный пример, когда он нужен
   для отдельной гарантии. Не добавляй тест, который лишь повторяет реализацию.
4. Проверь исходный контрпример и положительный контроль. Для оценщика нужен
   пример допустимого пути и существенного нарушения; для платформы — соответствующие
   гарантии сессии, изоляции, журналирования или обработки результата.
5. При изменении общего инструмента проверь затронутые сценарии. При изменении
   данных fixture проверь самостоятельность и целостность; локальный `artifacts/`
   не должен быть входом поддерживаемых тестов.
6. Обнови описание фактического поведения и оставшихся расхождений с концептом.
   Исправление защиты не разрешает отключать другие защиты или менять остальные задачи.

**Готово:** дефект воспроизведён и устранён, положительный контроль сохранён,
затронутые гарантии проверены; непроверенное междоменное или сценарное влияние
явно указано. Код возврата ошибки сам по себе не доказывает отсутствие эффекта:
проверяются данные и фактически переданные результаты.

## Как выбирать офлайн-проверки

Команды выполняются из корня репозитория после
`uv sync --frozen --extra dev --extra platform`; нужен `rg` в PATH.

| Изменение / цель | Команда или точка выбора | Граница свидетельства |
|---|---|---|
| Документация и структура Banking.ru | `make check-banking-repo`, затем `git diff --check` | Локальные ссылки и якоря, индекс задач, профили оценки и входы поддерживаемых тестов; без модели и регрессии |
| Эталон и бездействие одной задачи | `make test-banking-task TASK=2` | Ровно два контрольных маршрута; не все альтернативы и нарушения |
| Конкретная гарантия | `uv run pytest <файл>::<тест> -q` | Выбери существующий узкий тест или необходимые новые контроли |
| Общие контракты | `make check-banking-contracts` | Confidentiality, access, identity, discovery; проверяет согласованность, не полную валидность задач |
| Механизмы оценщика | `make test-banking-evaluator` | Поддерживаемая группа; не заменяет контроли конкретного задания |
| MCP, сессии, изоляция, поставка | `make test-banking-infra` | Поддерживаемая инфраструктурная группа; для небольшой правки можно выбрать отдельный тест |
| Harness и preflight | `uv run pytest tests/test_platform/test_codex_harness.py tests/test_platform/test_banking_preflight.py tests/test_platform/test_banking_startup_discovery.py tests/test_platform/test_codex_container.py -q` | Офлайн-проверки directory, совпадения поверхности, MCP-журнала и изоляции; тест настоящего Docker требует явно заданного BANKING_CODEX_TEST_IMAGE |
| Knowledge MCP | `uv run pytest tests/test_platform/test_knowledge_mcp.py -q` | Самостоятельный корпус, метаданные, страницы, grep без полных статей, cat/read, бюджеты и MCP HTTP; без моделей и миграции задач |
| Каталог и общий диспетчер | `uv run pytest tests/test_platform/test_bank_directory.py tests/test_platform/test_directory_session.py -q` | Пагинация, схемы, строгие аргументы, MCP, журнал, отдельные бюджеты и адресные контроли Bank 2; модель не вызывается |
| Банковские предметные регрессии | `make test-banking-regressions` | Более широкая группа; выбирается при соответствующем влиянии |
| Успешные и ошибочные вызовы инструментов | `make test-banking-tools` | Контракты инструментов всего набора, а не только одной задачи |
| Линт и формат перед коммитом | `make check-all` | Форматтер меняет файлы; проверь итоговый diff и не включай посторонние изменения |

`make check-banking-repo` требует только Python 3.10+ и ничего не записывает.
Проверяет корневые AGENTS/README, концепт, `docs/banking-ru/*.md` и связанные
инструкции домена, оценщика, тестов и fixtures. Ссылки проверяются внутри
репозитория; внешние URL не запрашиваются. Примеры в fenced/inline code
пропускаются. Якоря проверяются по Markdown-заголовкам ATX (`#`), включая
повторяющиеся заголовки; HTML-якоря и reference-style ссылки не поддерживаются.

Индекс читается существующим `task_store`: проверяются пути, имена, ID,
порядок и отсутствие JSON-файлов задач вне индекса. Профили сверяются с таблицей
«Какие профили сейчас исполняются» в `evaluation.md`; численность и ID не зашиты
в проверку. При миграции обновляй эту таблицу вместе с критериями.

Также проверяется наличие файлов из поддерживаемого runner тестов и литеральные
пути через `Path`, `/`, `open`, чтение JSON/задач и копирование входов: зависимости
от `artifacts/` и Wiki отклоняются. Это ограниченный статический контроль, а не
полный анализ потоков данных: динамически собранные пути могут остаться незамеченными.
Негативные примеры запрещённых путей в строках тестов не считаются зависимостью.
Команда не доказывает изоляцию, валидность задач, корректность оценки или смысловую
согласованность всего текста; проверка общих контрактов остаётся отдельной.

`make test-banking-basic` запускает эталон и бездействие всех 61 задач;
`make test-banking` — весь поддерживаемый компактный набор.
`make test`, `make test-all` и pytest без адресного выбора тоже могут значительно
расширить объём. Эти команды не являются обязательным шагом любой правки:
полную регрессию запускай только в отдельно разрешённом объёме.

Выбор поддерживаемых файлов находится в
[run_basic_tests.py](../../scripts/banking_ru/run_basic_tests.py). Новый файл
не включается в группу автоматически: изменение состава набора должно быть явным.
Не расширяй или повторяй проверки после успеха без новой причины.

## Маршрут 3: модельный эксперимент

**Вход:** корректная задача, проверенный оценщик, гипотеза и разрешённый объём попыток.
Сначала валидность, затем измерение сложности; целевой процент успеха определим
после пилота Bank 2. Новая документация или исправление кода не разрешают новые попытки.

1. Закрепи задачу, данные, корпус, оценщик, конфигурацию модели и бюджет попыток.
   Сформулируй гипотезу и контроли. Задача и среда не меняются между сравниваемыми
   попытками без явного разделения версий.
2. Подготовь отдельный набор входов и авторскую спецификацию preflight.
   Отдельный Solution Contract.md не создаётся. Старое поле `solution_contract`
   необязательно и поддерживается только для совместимости прежних спецификаций;
   существующие авторские отчёты можно включить в `inputs`.
   Спецификация связывает `task_id`, `data_dir`, `inputs`, `validation_command`,
   `evidence_env`, `controls`, `boundary`, модель и `max_attempts`.
   Контроли задают ожидаемый 0/1 и привязаны к версии; `boundary` содержит
   подтверждения границы и неизменяемого image ID. Схему и проверки сверяй с
   [banking_preflight.py](../../scripts/banking_ru/banking_preflight.py).
3. До обращения к модели выполни этапы поддерживаемого harness:

   ```sh
   uv run python scripts/banking_ru/run_codex_harness.py preflight seal --spec <spec.json> --out <output-dir>
   uv run python scripts/banking_ru/run_codex_harness.py preflight validate --out <output-dir>
   uv run python scripts/banking_ru/run_codex_harness.py preflight surface --out <output-dir>
   ```

   Это этапы без модели, но `validate` исполняет заданную команду проверки:
   её объём также должен соответствовать согласованной работе.
4. Проверь фактическую изоляцию и поверхность инструментов: отдельный контейнер,
   полный доступ Codex внутри него, без доступа к хосту, Wiki, репозиторию,
   эталонам и прошлым результатам; свежая MCP-сессия. Сохрани image ID и подтверждения.
   Успех preflight не расширяет границу разрешений или число попыток.
   Поддерживаемый harness и его preflight используют `directory`: один MCP-эндпоинт,
   на старте только bank_directory/bank_call. Surface packet закрепляет startup,
   итоговый prompt, обе схемы и max_calls/max_errors/max_discovery_calls; перед
   передачей тикета модели фактическая сессия должна совпасть с ним. В `model`
   можно явно задать положительный max_discovery_calls; при отсутствии лимит None,
   число discovery-вызовов всё равно учитывается отдельно. Старые surface packets
   без этой конфигурации не принимаются. Смена кода требует нового подтверждения
   физической контейнерной границы; локальная MCP-заглушка его не заменяет.

   С 30 октября 2026 используется Codex `app-server` с двумя явными dynamic tools,
   проксируемыми авторским брокером в банковский MCP. Обычный `codex exec`
   этой версии добавлял лишние инструкции и инструменты; старые подтверждения
   только банковского `tools/list` недостаточны. Полный доступ задаётся при
   `thread/start`: sandbox=danger-full-access, approvalPolicy=never,
   ephemeral=true; зачётный прогон не продолжает предыдущую сессию, fallback
   модели запрещён. Отдельно разрешённая диагностика после фиксации результата
   описана в разделе [продолжения сохранённого thread](#диагностическое-продолжение-сохранённого-thread--11-ноября-2026);
   она не считается новой независимой попыткой задачи.
   С 1 ноября 2026 контейнер запускается с `network=none` и read-only root.
   Домашний каталог и рабочая папка перед запуском пусты; банковская
   инструкция передаётся сообщением API, без файла AGENTS.md. `auth.json` и переменные с токенами в контейнер не передаются.
   Подписочная авторизация загружается только доверенным шлюзом на хосте.
   После попытки контейнер
   удаляется вместе с новым локальным состоянием.

   Внутри контейнера работает только loopback HTTP relay; его обмен с хостом
   идёт по stdio `docker exec`, без host socket/volume и без сетевого маршрута.
   [codex_broker.py](../../scripts/banking_ru/codex_broker.py) разрешает только
   фиксированный inference endpoint, модель и effort текущего прогона.
   Account/history API, redirects, proxy из окружения и fallback на API key
   запрещены. Авторский MCP-брокер работает на хосте отдельно от контейнера.

   По решению пользователя от 11 ноября 2026 текущий режим брокера —
   `history_mode=observe`. Контекстом, сокращением и сводками управляет Codex.
   Брокер записывает запросы и ответы для последующего аудита, но не сравнивает
   продолжение с накопленной историей и не создаёт для него собственную сводку.
   Проверяются чистый первый запрос, исходные startup/тикет/схемы, разрешённые
   модель и effort, параметры транспорта и отсутствие дополнительных инструментов.
   Изменение текста истории само по себе не останавливает прогон.
   RPC по-прежнему сверяется с фактически полученными call_id и аргументами;
   исполнение допускается один раз, после проверки полного SSE-потока до EOF.
   Реальные результаты банковских операций сохраняются независимо от того,
   как Codex впоследствии представляет их в контексте. Брокер не читает закрытое
   хранилище, Wiki или эталоны и не добавляет их в запросы.

   Локальный запрос compaction распознаётся по служебным метаданным CLI или
   штатному prompt; его ответ не считается финальным сообщением клиенту.
   Событие `compaction_observed` фиксирует факт такого обмена без проверки
   тождественности последующей сводки. Полная трасса остаётся на хосте для аудита;
   это не доказательство целостности внутренней истории агента. Проверка артефакта
   явно возвращает `context_integrity_verified=false`. Старые артефакты без поля
   `history_mode` воспроизводятся по прежнему строгому контракту; их результаты
   не переинтерпретируются. Контейнерная изоляция и доступ к текущей банковской
   сессии сохраняются. Endpoint `/responses/compact` не открывается.
   Офлайн-проверки: `artifacts/broker-observe-context/report.md`.

   Физический отчёт содержит `cli-request.json` с полным захваченным запросом,
   `request-contract.json` с ожидаемыми model/effort/startup/prompt и схемами,
   `broker-evidence.json` с происхождением продолжений, `isolation.json` с
   Docker/network/file/apply_patch-пробами и эффективные параметры thread/start.
   Boundary gate заново сравнивает
   весь первоначальный запрос и объявления инструментов по контракту профиля.
   Наследованная история в первом запросе, внешний continuation ID,
   дополнительный инструмент или parallel_tool_calls=true блокируют gate.
   Текст последующей истории в режиме observe не сравнивается.
   Дополнительно он воспроизводит положительный цикл минимум трёх inference
   запросов и двух MCP-вызовов. Старые отчёты с bridge-сетью или guest auth
   больше не дают пройти ворота. Физическая проверка использует только заглушку.
   Проверка через HTTP-заглушку не вызывает модель и не подтверждает отсутствие
   серверного prompt cache; локальная история и серверный кэш — разные гарантии.
   Брокер сохраняет исходные app-server events и совместимый журнал сообщений
   и MCP-вызовов, включая частичный результат при техническом сбое.
   Технические пределы транспорта: 512 запросов на попытку, 2 MiB на вход,
   16 MiB на ответ, 128 MiB на журнал входов/событий, 120 секунд на один
   upstream-поток плюс общий timeout попытки. Внутренний HTTP relay ограничивает
   бездействие при загрузке запроса 15 секундами; после получения полного тела таймаут
   отключается, чтобы не оборвать допустимое ожидание ответа или паузу SSE.
   Ожидание результата по-прежнему ограничено таймаутом хоста.
   До первого доставленного байта и при отсутствии элементов ответа допускается
   до трёх отправок одного inference-запроса при транспортном сбое, временном
   HTTP-отказе или error-событии без известной постоянной причины. Вся группа
   ограничена теми же 120 секундами, все физические отправки — общим лимитом 512.
   Известные ошибки безопасности/авторизации, невалидная история и частичный
   ответ не повторяются. Транспортный сбой после любых полученных байтов также
   не повторяется, включая данные, ещё удерживаемые фильтром секретов. Повторы учитываются отдельно в broker_evidence.retries;
   ни модель, ни содержимое запроса не меняются, MCP не исполняется повторно. Это ограничения инфраструктуры,
   не дополнительные критерии бизнес-оценки; превышение не доказывает ошибку
   банковского решения. Числовой discovery-бюджет по-прежнему задаётся отдельно.
   Для сохранения полных результатов MCP каталог модели
   задаёт `truncation_policy` в 500000 токенов. Это не увеличивает допустимый
   размер запроса брокера: при превышении 2 MiB попытка технически завершается;
   такие крупные результаты и ограничение контекста модели требуют отдельной
   обработки. Проверка содержимого и происхождения истории сохраняется.

   JSON-объекты и массивы в текстовых блоках MCP перед передачей Codex
   сериализуются с `ensure_ascii=False`: русские документы не раздуваются
   последовательностями `\uXXXX`. Значения JSON сохраняются; обычный текст,
   скалярные ответы и маркер завершения передаются без изменений. Исходный
   MCP-ответ остаётся в журнале, а host ledger закрепляет именно доставленный
   текст и по-прежнему требует его точного воспроизведения. Автоматическое
   сжатие контекста не является разрешённой заменой истории: достижение
   контекстного предела остаётся техническим ограничением, а не ошибкой Bank 2.

   Если агент оставил сессию открытой, harness вызывает host-control `abort`,
   затем получает нулевой результат и закрывает сессию. В MCP `done` за агента
   не вызывается. `missing_done` означает DB=0/ACTION=0 и `fail_missing_done`.
   Полученный `run` (stdout/stderr, app-server events и host broker ledger)
   сохраняется и при последующих ошибках состояния, результата, обработки
   журнала или cleanup. `record.json` записывается до обогащения серверным
   журналом и остановки сервера; вторичные ошибки cleanup не заменяют исходную.
   Это сохранение полученных данных при обрабатываемых сбоях, а не гарантия
   восстановления после SIGKILL, потери диска или отключения питания.
   Ошибки inference-брокера дополнительно сохраняют этап и безопасный код
   причины; HTTP-отказ сохраняет числовой статус. Неизвестные исключения
   обозначаются `unclassified`: их сообщения, заголовки и тела ответов в
   диагностический блок не записываются.
   Из событий `error`, `response.failed` и `response.incomplete` сохраняются
   только известные коды причины из фиксированного списка; незнакомые значения
   обозначаются `unknown`. Это не позволяет восстановить причину старого
   прогона, если исходное событие не было сохранено.

   Адресная физическая проверка нового транспорта и MCP roundtrip без модели:
   `BANKING_CODEX_TEST_IMAGE=<проверенный sha256:image> BANKING_CODEX_TEST_MODEL=<модель> uv run pytest tests/test_platform/test_codex_container.py -q`.
   Если модель не указана, заглушка проверяет `gpt-6.1-sol`; модель физической
   квитанции должна совпадать с моделью preflight, каталог берётся из закреплённого образа.
   Зелёные проверки этого транспорта не разрешают модельный прогон и не заменяют
   полный физический отчёт текущей версии runtime для preflight.
5. Только после успешных ворот и разрешения на конкретный объём запусти:

   ```sh
   uv run python scripts/banking_ru/run_codex_harness.py --preflight-dir <output-dir>
   ```

6. Сохрани исходный журнал, оценки, технический исход, версии, эффективную команду,
   модель, параметры и лимиты. Проанализируй причины: ошибка модели, дефект задачи,
   оценщика или инфраструктуры. Отказ агента решить поручение — неуспех попытки;
   технический сбой отдельно не доказывает конкретную банковскую ошибку модели.

**Готово:** выполнен разрешённый объём, результаты воспроизводимо привязаны
к версии, указаны число попыток и доля успехов, причины и ограничения выводов.
Один ноль не доказывает устойчивую сложность. Исторические баллы не пересчитываются.

## Langfuse: трассы завершённых попыток

Сверено 5 ноября 2026. Проект — [Banking.ru Evaluation](https://langfuse.158.160.161.24.sslip.io/project/cmvr30y9y0003qa2n4ktr5phq),
доступен по HTTPS без SSH-туннеля. Адрес содержит динамический IP VM: при его
смене обнови `LANGFUSE_BASE_URL`/`LANGFUSE_HOST` в локальном файле ключей и URL
MCP, затем повтори health, проверку проекта и чтение трассы. Не создавай новый
проект только из-за смены адреса.

Перед работой проверь health API и проект по ключу. MCP `langfuse_banking_ru`
подключается к `<LANGFUSE_BASE_URL>/api/public/mcp` с проектной Basic-авторизацией
через локальный `http_headers_helper`. В Codex сохраняем allowlist операций
чтения: observations, scores, metrics и `getMedia` для вложений.
Если изменённая конфигурация ещё не загружена в текущем чате, не заявляй наличие
инструментов: переподключи MCP или используй тот же Streamable HTTP endpoint;
CLI/API остаются доступным запасным способом чтения.
Проверяемому агенту этот MCP и его ключи не передаются.

После разрешённой модельной попытки публикуй сохранённую траекторию и проверяй
доставку через MCP. Для A2A/SDK используй общую команду ниже, а не отдельные
конвертеры с вручную вписанными оценками. Старый harness может автоматически
экспортировать `record.json`. В коде экспорт выключен по умолчанию; в локальном
`langfuse.env` включён `BANKING_LANGFUSE_ENABLED=true`:

```sh
set -a
source ~/.config/agent-evaluation/langfuse.env
set +a
export BANKING_LANGFUSE_ENABLED=true
uv run python scripts/banking_ru/run_codex_harness.py --preflight-dir <output-dir>
```

Это команда модельного запуска: по-прежнему нужны preflight и разрешённый объём.
Файл ключей локальный, вне Git, с правами `0600`. Для другой машины нужно отдельно
подготовить свои проектные ключи и доступный `LANGFUSE_BASE_URL`.

Импорт уже завершённого A2A/SDK-прогона **не вызывает модель**:

```sh
set -a
source ~/.config/agent-evaluation/langfuse.env
set +a
uv run --with langfuse==5.0.4 python -m tau2.platform.langfuse_export --sdk-attempt <attempt-directory>
```

Команда читает сохранённые `evaluation-input.json`, `evaluation.json`,
`sdk/task-input.json`, `native-run.json`, `started.json` и при наличии `calls.jsonl`.
Тикет, стартовые инструкции, фактический вход агента, результаты и оценки берутся
из этой попытки, а не из текущей версии задачи. Проверяются совпадение задачи,
наличие тикета во входе, модель, счётчики, завершение и DB × ACTION; хеши входных
файлов записываются в metadata. Это проверка согласованности экспорта, не замена
независимому replay и аудиту валидности прогона.
Сохраняются все банковские/discovery-действия, доступные сообщения и workbench,
баллы из SDK и доступные метрики брокера. Полный журнал с порядком событий остаётся
локальным первоисточником. Повтор команды с прежними входами и подтверждением
`submitted` для того же назначения не отправляет события второй раз.

Экспортёр [langfuse_export.py](../../src/tau2/platform/langfuse_export.py)
исполняется в отдельном окружении `uv` с Python SDK `langfuse==5.0.4`.
Он не меняет основные зависимости τ-bench и не устанавливается внутрь
модельного контейнера. Первая отправка может потребовать загрузки зависимостей.

Одна попытка — одна трасса: тикет, доступные сообщения из Codex JSON, фактические
MCP-операции с исходными аргументами, результатами и ошибками, балл и компоненты.
Для связанного прогона экспортёр читает серверный журнал по platform_event_path,
проверяет SHA-256, ID сессии и задачи. Отсутствующий или повреждённый журнал
не заменяется пустым списком событий.
API-ключи и сессионный токен исключаются; банковские данные синтетического набора
в аргументах и результатах сохраняются для разбора процесса. Не загружай в этот
проект реальные клиентские данные или секреты инфраструктуры.

Это постфактум-экспорт, а не покадровая трансляция обращений Codex к модели:
полные запросы и ответы каждой генерации в эту трассу не импортируются;
скрытые рассуждения не восстанавливаются. SDK-импорт сохраняет начальный вход
агента и суммарные токены/число запросов из брокера, если они были записаны.
Стоимость подписки остаётся неизвестной, не нулевой. Времена spans
показывают импорт; исходные времена MCP-запросов и результатов находятся
в метаданных старого формата, а для SDK — в локальном `calls.jsonl`; поэтому
latency этих spans не является длительностью решения. Метрика `resolution_seconds`
SDK считается от первого `agent.turn` до последнего записанного конца вызова;
при отсутствии этого журнала используется native elapsed с явной отметкой источника.
Хронологию сверяй по исходным событиям, а не по порядку импортированных узлов.

Результат отправки записывается отдельно в `langfuse-export.json` рядом с попыткой.
`submitted` означает выполнение отправки и flush, а не независимую проверку
доставки. Ошибка экспорта не меняет `record.json`, бизнес-балл или разрешённое
число попыток. При первичной настройке проверяй доставку чтением через API/MCP.
Ручной повтор старого `--record` может создать дополнительные наблюдения в той же
трассе; SDK-команда защищает от обычного повторного импорта сохранённой попытки.
Потеря подтверждения после частичной отправки всё ещё требует проверки сервера
перед повтором. Исторические запуски автоматически не импортируются.

При проверке через MCP: прочитай все страницы `listObservations` по `traceId`
и временному диапазону, затем `listScores`. При запросе input/output используй
страницы не более 50 записей и передавай `cursor` до конца выдачи.
Сверь количество действий, исходные
аргументы/результаты, DB/ACTION и метаданные версии с локальными файлами.
Для разбора конкретного шага используй `getObservation`, для медиа — `getMedia`.
Успешный health или `submitted` не заменяет эту проверку. Недоступность Langfuse
фиксируется отдельно и не превращает правильное банковское решение в ноль.

## Когда обновлять документы

Обновляй действующую документацию в той же работе, что изменяет описываемое
поведение. Файлы задач и код определяют факт реализации; документы объясняют
его и отмечают принятые, но ещё не реализованные решения.

| Что изменилось | Что сверить и обновить |
|---|---|
| Цели или принятые принципы | [Концепт](../banking-ru.md), противоречащие инструкции и соответствующие подробные руководства |
| Компоненты, границы, доступ модели | [Архитектуру](architecture.md), фактические гарантии и открытые вопросы |
| Хранение, загрузка или поля задания | [Формат задачи](task-format.md), README данных и ссылки на исполняемую схему |
| Проверки или профиль оценки | [Оценку](evaluation.md), статус миграции, списки задач и количества во всех затронутых документах |
| Команды или процесс разработки | Этот документ, корневой [AGENTS.md](../../AGENTS.md), соответствующий README |
| Условия конкретного задания | Критерии и контроли той же версии, отчёт; при ведении Wiki — карточку каталога и статус реестра |

Укажи дату содержательной сверки, проверь ссылки и якоря. Не обновляй дату
или статус «проверено» без соответствующей проверки. Исторический отчёт описывает
свою версию и не переписывается под новую реализацию. Устойчивые выводы переноси
в существующее руководство со ссылкой на доказательства.

Обязательные правила разработки должны быть доступны в репозитории. Wiki
служит дополнительным исследовательским и отчётным контекстом, а не скрытой
зависимостью, без которой невозможно изменить и проверить код.

### Проверяемый runtime и диагностика — 2 ноября 2026

Для GPT-6.1 Terra проверяется контейнер Codex `0.166.0-alpha.5.1`;
образ закрепляется по SHA-256 в spec конкретного прогона. Каталог моделей
извлекается из этого же образа; отсутствие выбранной модели блокирует запуск.
Новую версию сначала проверяют локальной заглушкой с выбранной моделью,
включая полный запрос, многошаговый MCP, сеть, файловую границу и очистку.

Новые исходы модели называются `pass`/`fail`, независимо от имени модели.
Исторические `luna_pass`/`luna_fail` не переписываются и остаются читаемыми.
`event_observation.broker_trajectory` отдельно сообщает результат воспроизведения
host-ledger: `verified`, `unverified` или `unavailable`. Его область — полученные
хостом ответы и авторизованные банковские RPC. Он не подменяет физический
preflight и не объявляет старый CLI capture полным.

Дополнительные диагностические показатели описаны в
[банковской оценке](evaluation.md#дополнительные-метрики--2-ноября-2026).
Подписочный транспорт сохраняет только числовые input/output/total tokens из
полученного usage; неизвестные токены и стоимость обозначаются null.

## Версии проверяемых агентов: Workbench V1

По решению 2 ноября 2026 создаём отдельный профиль `v1` (`codex_workbench`,
версия `V1`). `baseline` остаётся прежним чистым Codex. Номера версий назначает
пользователь: автоматически создавать V2 или заменять V1 следующим вариантом
нельзя. Версию идентифицируют имя, Git commit и SHA-256 исходника профиля;
результаты существующих версий не переписываются. Исходник V1:
`src/tau2/platform/agents/v1.py`; общий выбор профиля — соседний `__init__.py`.

V1 получает тот же банковский startup, тикет и MCP, а также общую методику
работы и локальный инструмент `workbench`: `set`/`get` для JSON-заметок текущей
попытки, `compute` для Python. Факты/источники записывает агент: оболочка не
доказывает их истинность. Python получает `data`, возвращает `result`; переменные
Python не сохраняются, JSON можно перенести через заметки. Заметки ограничены
64 KiB; расчёт — 2 CPU-секунды, 128 MiB адресного пространства, 5 секунд ожидания,
64 KiB stdout и 32 KiB JSON-результата. Произвольный Python не считается
безопасным сам по себе: граница безопасности — Docker без сети, host mounts и
авторизации в госте. Доступ к банковским данным/действиям остаётся через MCP.

Образ V1 строится отдельно из проверенного локального baseline-образа:

```sh
mkdir -p /tmp/banking-v1-build
DOCKER_BUILDKIT=0 docker build -f "$PWD/scripts/banking_ru/Dockerfile.workbench-v1" -t banking-codex-workbench:v1 /tmp/banking-v1-build
```

Перед сборкой сверить ID базового образа с комментарием Dockerfile. При сборке
версии Python зависят от Debian-репозитория; воспроизводимый запуск закрепляет
фактический итоговый image ID, а не только Dockerfile или изменяемый tag.

Для будущего модельного эксперимента spec содержит `"agent_profile": "v1"`
и `model.image` с проверенным ID образа V1. Тот же поддерживаемый harness
вызывает `run_one_attempt(..., agent_profile="v1")`. Запуск по-прежнему требует
отдельно разрешённого объёма и свежих seal/validate/surface/boundary; физическая
квитанция baseline не подходит V1. В полном запросе V1 ровно три разрешённых
инструмента: bank_directory, bank_call и фиксированная схема workbench.
Baseline по-прежнему допускает ровно два. Неверные профили и подменённые схемы
отклоняются. Модель, reasoning и банковские бюджеты задаются независимо от версии.

Манифест профиля, хеш исходника и локальные вызовы сохраняются в
`record.run.agent_profile` и `record.run.workbench_events`, полный брокерский
журнал сохраняет исходные вызовы/ответы. Эти данные только для автора эксперимента;
агент не получает оценщик, другие попытки или эталон. Локальные вызовы не расходуют
банковский бюджет; их количество/затраты нужно учитывать отдельно при сравнении.
Задачи и бизнес-оценка общие для обоих профилей. Повышение качества пока не доказано:
создание V1 и проверки заглушкой не являются модельным экспериментом.


### Таймаут ответа модели — 3 ноября 2026

Хостовый брокер ограничивает отдельную попытку inference 300 секундами;
connect timeout — 20 секунд. Общий timeout_seconds прогона сохраняется отдельно.
Таймаут до первого доставленного/авторитетного ответа допускает до двух повторов
того же запроса в пределах общего бюджета. После начала ответа повтор запрещён:
частично полученную траекторию нельзя незаметно заменить новой генерацией.
Прежний общий предел 120 секунд на запрос вместе с повторами мог прервать законное
ожидание; timeout теперь обрабатывается внутри попытки. Таймаут сам по себе
не доказывает отказ модели или ошибку банковской задачи.


### Журнал при завершении A2A — 4 ноября 2026

После ответа на done координатор может завершить попытку раньше естественного
завершения runtime. При такой отмене накопленные stdout/stderr, app-server
события, broker_evidence, request_contract и workbench_events сохраняются как
partial_run исходного CancelledError. Контейнерный harness добавляет inspection
и результат cleanup. A2A сохраняет этот объект в runtime своего JSON-артефакта
вместе с a2a_events и status=canceled; бизнес-завершение определяется журналом
платформы, а не exit_code отменённого runtime.

Снимок не объявляется полным естественным завершением модели: cancelled=true,
exit_code=1; неизвестный usage не восстанавливается. Не заменять им проверку
done/DB/ACTION и не считать обычное прерывание до done успешной попыткой.
Гарантия относится к обработанной отмене процесса, не к SIGKILL или потере диска.
Адресная физическая проверка без модели:
`BANKING_CODEX_TEST_IMAGE=<sha256> BANKING_CODEX_TEST_MODEL=gpt-6.1-sol uv run pytest tests/test_platform/test_codex_container.py -q -k 'a2a_cancel or a2a_v1'`.

### Причины ошибок inference и safety — 11 ноября 2026

Брокер сохраняет в `broker_evidence.errors` поле `classification`:
`safety_block` только при явном `content_filter` или известном структурированном
`misalignment.error_type` в терминальной ошибке; `technical_error` при известных
транспортных/протокольных причинах; `provider_error_unknown` при неизвестной
причине; `generation_limit` при лимите генерации; `interrupted` при `steered`;
`broker_error` для остальных локальных ошибок брокера. Это диагностика,
не изменение DB × ACTION и не доказательство успеха атаки.

`provider.fields` сохраняет пути полей code/type/reason, известные значения,
размеры и SHA-256. Неизвестные коды и свободные сообщения сохраняются только
как размер/хеш: исходный текст, заголовки авторизации и prompt не выводятся.
Хеш нужен для сопоставления событий, а не для восстановления причины.
Неизвестный конкретный code нельзя объяснить одним общим error.type.
HTTP-ошибки также разбираются: JSON-тело ограничено 8 KiB; слишком длинное
тело отмечается body_truncated и не классифицируется по его фрагменту.
HTTP 403 и слово safety в свободном сообщении сами по себе не доказывают отказ.

Терминальная запись содержит номер запроса, `relay_response_started`, число
`response_bytes_forwarded`, `output_started`, `model_refusal_observed`,
`response_completed`, `retryable_by_reason`. Последнее — допустимость повтора
по причине, не разрешение повторить частично переданный ответ: существующие
проверки доставки и целостности истории сохраняются. Явная safety-причина
запрещает автоматический retry даже при HTTP 429/5xx.

Структурированный отказ модели фиксируется отдельно: завершённый ответ получает
`response_signals.model_refusal` в событии response_completed; отказ, замеченный
до ошибки, отражается в model_refusal_observed. Обычная фраза отказа в output_text
не классифицируется по ключевым словам. Refusal не равен блокировке выдачи,
а байты, переданные в контейнер, не доказывают доставку сообщения клиенту банка.
В SDK по-прежнему нужен банковский журнал фактических действий.

Проверка без модели: `uv run pytest tests/test_platform/test_codex_broker.py -q`.
Тесты используют локальные SSE-генераторы и httpx.MockTransport, без реальной
авторизации/внешних запросов. Старые unknown-ошибки не переклассифицируются.
После изменения брокера прежняя physical/preflight-квитанция не подтверждает
новую версию runtime; до будущего live-прогона понадобится свежая проверка.
Модельные запуски этой работой не разрешаются.

Контракт полей публичного Responses API:
[streaming events](https://developers.openai.com/api/reference/resources/responses/streaming-events),
[response errors and incomplete details](https://developers.openai.com/api/reference/resources/responses/methods/retrieve).
Подписочный Codex endpoint может возвращать иные значения: они остаются unknown,
а не получают автоматически придуманную safety-классификацию.

### Сохранение диагностической сессии — 11 ноября 2026

По явному запросу пользователя `codex_engine` / `invoke_isolated_codex` допускают
`retain_session=True`. Контейнер по-прежнему создаётся пустым и изолированным,
без mounts/сети/credentials; thread/start использует ephemeral=false и проверку
отсутствия прежних turns/fork. После измерения inference relay закрывается,
процесс app-server останавливается, но контейнер и нативная история остаются.
Новый app-server проверяет `thread/read` без turn/start и без модели. В артефакте
`container.retained=true`, `cleanup_verified=false`, `native_thread_id` и
`retention_check` явно отличают удержание от удаления. Стандартный режим удаления
не меняется. Preflight проверяет фактическое ephemeral согласно retain_session.
Сохранение не разрешает новые запросы модели. Банковская оценка фиксируется до
ручных продолжений; закрытый через done банковский эпизод не переоткрывается.
История находится в tmpfs работающего контейнера: до экспорта нельзя останавливать
или перезапускать Docker. Нативное чтение проверяется локальным stub без модели.


### Диагностическое продолжение сохранённого thread — 11 ноября 2026

`invoke_app_server` принимает совместно `resume_thread_id`, `resume_contract` и
`retain_session=True`. Используется native thread/resume, без конструирования
старой переписки разработчиком. Проверяются прежний thread ID, непустая история,
тот же model/effort/startup/набор инструментов. Брокер допускает у первого запроса
контекст только в явно выбранном resumed+observe режиме; свежие прогоны сохраняют
запрет наследованной истории. Проверки инструментов, envelope и авторизации
вызовов сохраняются. Ручные продолжения закрытого Bank 2 не меняют оценённую БД:
банковские вызовы получают статус закрытой сессии. Запросы и сырые SSE сохраняются
в private store, публичный отчёт содержит хеши и причины остановки.
