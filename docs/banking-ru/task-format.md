# Формат банковской задачи

Справочник для автора: что хранится в задании, кто получает его части и как
они связаны. Сверено с рабочим деревом 28 октября 2026 года.
Правила и цели — в [концепте](../banking-ru.md), компоненты и границы доступа —
в [архитектуре](architecture.md).

## Целевое разделение файлов

Принято разделить текст поручения, сценарий и критерии физически.
С 28 октября 2026 года все 61 задание разделены на три файла. Разделение меняет хранение, а не содержание задания.

| Файл | Содержание | Потребитель |
|---|---|---|
| `ticket.md` | Только текст обращения клиента: проблема, цели, известные обстоятельства и ограничения | Агент получает текст |
| `scenario.json` | Начальное состояние и сценарные данные | Банковская среда |
| `evaluation.json` | Эталон, критерии DB и ACTION, допустимые результаты | Оценщик |

Задания хранятся в `tasks/bank_NNN/` от `bank_001` до `bank_061`. Индекс ссылается на `scenario.json` в каждом каталоге;
`ticket.md` и `evaluation.json` лежат рядом
и имеют фиксированные имена. `scenario.json` содержит `id` и все прежние
поля верхнего уровня, кроме `ticket` и `evaluation_criteria` — в том числе
авторские `description`, `user_scenario` и `scenario_version`.
`evaluation.json` содержит непосредственно прежний объект `evaluation_criteria`,
без дополнительной обёртки. `ticket.md` — точная UTF-8 строка прежнего `ticket`,
без добавления перевода строки. Сценарий не может дублировать тикет или критерии.
Загрузчик собирает прежний объект `Task`; общая исполняемая модель не меняется.
В `ticket.md` не добавляются YAML-метаданные, критерии, эталон или авторский план.
Общий startup и доступ к MCP выдаются отдельно от текста тикета.

Файлы сценария и оценки не передаются модели и не доступны через корпус,
поиск документов или файловую систему её процесса. Исходное состояние
предоставляется агенту только посредством разрешённых банковских инструментов.
Раздельное хранение помогает контролю доступа, но не заменяет изоляцию.

## Как задачи хранятся сейчас

[Индекс tasks.json](../../data/tau2/domains/banking_ru/tasks.json) содержит
упорядоченный список `task_files`. Его элементы указывают на `tasks/bank_NNN/scenario.json`. Номер файла или каталога должен соответствовать
ID: `bank_002/scenario.json` → `Bank 2`. Порядок набора определяется индексом.

Во всех 61 заданиях эти части разделены на три файла.
[task_store.py](../../src/tau2/domains/banking_ru/task_store.py) проверяет пути,
уникальность ID и соответствие имени файла; затем
[environment.py](../../src/tau2/domains/banking_ru/environment.py) валидирует
объекты общей моделью `Task`. Загрузчик также читает старый массив задач
для сохранённых снимков. Банковских splits сейчас нет.

Для поддерживаемого чтения и записи используются `load_tasks`, `task_outputs`
и `write_tasks` из `task_store`. Они сохраняют формат существующей задачи и байты
неизменённых частей. `task_inputs` перечисляет индекс и все части задач для
копирования и контроля изменений; `render_task_patch` адресует реальные файлы.
Для изменения тикета без конечного LF или с CRLF используй `write_tasks`:
текстовый patch не сохраняет такие окончания строк и отклоняется явно.
Чтение и запись сохраняют точные байты тикета; LF автоматически не добавляется. При копировании текущего набора нужны индекс
и каталог задач вместе. Отдельный файл задачи не заменяет общие данные среды.

### Поля текущей Task

Исполняемый источник формата — [tasks.py](../../src/tau2/data_model/tasks.py).
Таблица поясняет модель, а не требует заполнять все необязательные поля.

| Поле | Назначение |
|---|---|
| `id` | Обязательный идентификатор задания |
| `ticket` | Текст поручения для тикетного режима; в общей модели допускается отсутствие, для нашего целевого входа нужен текст |
| `description` | Авторские сведения: цель, применимые правила и заметки; не агентский startup |
| `user_scenario` | Обязательное поле общей модели τ-bench для пользовательского сценария; не заменяет выдаваемый банковскому агенту тикет |
| `initial_state` | Необязательное начальное состояние; `null` означает отсутствие отдельного наложения задачи |
| `evaluation_criteria` | Критерии и эталон; скрытая от проверяемой модели часть |
| `issues` | Необязательные авторские замечания |
| `required_documents` | Необязательные названия документов в общей схеме; сами по себе не заменяют исполняемые проверки получения источника |
| `user_tools` | Настройка пользовательских инструментов общей модели; не разрешает менять общий банковский каталог по ID задачи |

В сырых JSON могут встречаться дополнительные исторические атрибуты, например
`scenario_version`. Он не объявлен полем текущей `Task`; наличие ключа в JSON
не доказывает его использование оценщиком. Не добавляй новые служебные поля
без явного потребителя и согласованной схемы.

### Начальное состояние и общие данные

`initial_state` содержит `initialization_data`, `initialization_actions`
и `message_history`. Эти возможности общей схемы не означают разрешение
передавать проверяемому агенту прошлые решения или историю других попыток.

Общая исходная БД находится в `db.json`, клиентские ответы — в
`intake_answers.json`, знания и политики — в `corpus/`. Manifest фиксирует
хеши этих входов. Сценарные ответы могут иметь область `task_id`, но не меняют
общую доступность систем, инструментов и документов. Подробности — в
[README набора](../../data/tau2/domains/banking_ru/README.md).

## Критерии и эталон в текущем формате

Механика исполнения и диагностики подробно описана в [банковской оценке](evaluation.md).

| Группа полей | Что задаёт |
|---|---|
| `reward_basis`, `banking_contract_version` | Формулу оценки и профиль миграции |
| `business_process_only`, `completion_mode`, `action_reward_scope` | Профиль процесса, завершение и объём проверки ACTION |
| `actions` | Эталон для получения ожидаемого состояния и объявления необходимых действий |
| `db_state_checks`, `db_alternative_action_*` | Конечные обязательства вне хеша и объявленные альтернативы эталона |
| `result_argument_bindings` | Связь зависимого аргумента с фактически полученным результатом, например созданным ID |
| `result_evidence`, `argument_evidence`, `action_order` | Полученные основания, аргументы и зависимости |
| `tool_access_policy`, `banking_confidentiality_contract` | Контроль доступа и подключение общих проверок конфиденциальности |
| `forbidden_actions` и специальные предметные контракты | Запреты и условия истории конкретного процесса |
| `env_assertions` | Сохраняемые проверки прежних банковских контрактов; у мигрированной группы не используются |

Фактические профили и состав мигрированной группы поддерживаются в
[руководстве оценки](evaluation.md#какие-профили-сейчас-исполняются). Обновление
этого справочника не мигрирует задачи и не подтверждает соответствие оценщика
всем новым решениям.

### Как читать action

Иллюстрация структуры, не готовый эталон или новая задача:

```json
{
  "action_id": "identify_customer",
  "requestor": "assistant",
  "name": "find_customer",
  "arguments": {"phone": "+7 900 000-00-00"},
  "compare_args": ["phone"],
  "required_for_reward": true
}
```

`action_id` связывает критерии внутри задания; `name` и `arguments` задают вызов.
`required_for_reward=false` оставляет шаг в эталонном воспроизведении, но не
делает его самостоятельным обязательным совпадением ACTION. Другие зависимости
могут отдельно требовать полученный этим шагом результат.

`compare_args` ограничивает сравниваемые аргументы: отсутствие или `null`
означает сравнение всех, `[]` — отсутствие сравнения аргументов этим списком.
Это не отключает отдельные проверки аргументов, доступа или источников;
для полного чтения файла действуют специальные правила совпадения пути.

`result_contains` и `result_patterns` проверяют результат инструмента,
а не финальную прозу. Само наличие ожидаемого вызова не доказывает успешность,
получение нужного основания или правильную конечную БД.

## Правила подготовки изменения

- Согласуй тикет, доступные данные и источники, допустимый результат и критерии.
- Каждый обязательный вызов, аргумент и источник обоснуй бизнес-процессом.
- Сохраняй альтернативные допустимые решения и общую среду набора.
- Не удаляй пустое поле автоматически: `null`, отсутствие и `[]` могут иметь
  разный смысл. Сначала сверь значения по умолчанию и потребителей.
- Не дублируй эталон и JSON критериев в отдельном `solution.md`.
- Проверяй изменение адресно по [процессу разработки](development.md).

Перенос остальных задач выполняется отдельно. Поддержка трёх файлов не меняет
выдачу агенту: платформа передаёт только собранный `ticket`. Разделение файлов
не подтверждает изоляцию само по себе; проверки доступа и контейнерная граница
сохраняются.

## Контракт полного чтения источников

`evaluation_criteria.banking_source_read_contract: "knowledge_v1"` включает
эквивалентный зачёт file_read/cat/read_document в мигрированной задаче db_action_v1.
По умолчанию поле отсутствует, и поведение остальных доменов/задач сохраняется.
Снимок корпуса передаётся оценщику через source_corpus, источники и зависимости
по-прежнему задаются actions/result_evidence. Правила проверки — в
[knowledge MCP](knowledge.md#единый-зачёт-полного-чтения-в-action).

## Происхождение версии при передаче дела

Опциональный banking_business_contract.case_review содержит customer_id и case_id.
Он включает ACTION-проверку полученной версии при успешной submit_cashback_review;
конечный статус, состав и сумма передачи относятся к DB. Раздельные дополнения
и повторная передача допускаются с полученными подходящими версиями.
Контракт не задаёт единственный порядок независимых чтений. Пример применения —
[Bank 2: связанные цели](evaluation.md#bank-2-выплата-и-передача-остатка--29-октября-2026).

## Составное урегулирование

Bank 2 v7 добавляет предложение обычными данными initial_state, не исключением
доступности по task ID. Меню и бюджеты — банковские факты, трактовка условий —
общие знания. reward_business_contract проверяет допустимость выбора по
полученным условиям; эталон DB задаёт максимальный результат. См.
[составное урегулирование](evaluation.md#bank-2-составное-урегулирование--29-октября-2026).
