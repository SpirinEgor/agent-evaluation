# Banking.ru: 61 банковская задача

Набор содержит `Bank 1` … `Bank 61`, исходную БД, фиксированные ответы клиента,
общий корпус знаний и политики. У всех задач одна агентская среда и общий набор инструментов.
Меняются запрос клиента, предметное состояние, ответы и критерии оценки.

Это синтетический банк. Условия продуктов и операции заданы данными симуляции;
они не являются инструкцией по обслуживанию клиентов конкретного реального банка.

## Установка после клонирования

Нужны Python 3.12 или 3.13, `uv` и `ripgrep` (`rg` в PATH).
Установите ripgrep средствами своей ОС, например `brew install ripgrep` на macOS
или `apt install ripgrep` на Debian/Ubuntu.

Из корня репозитория:

```sh
uv sync --frozen --extra dev --extra platform
make test-banking-package
```

Для офлайн-проверок API-ключи и установленный Codex не нужны.
Запуск самой модели требует её клиента и соответствующей авторизации.

## Единый регламент подписок

Процесс подписок, рекуррентных списаний и приёма связанной претензии находится
в `corpus/policies/subscriptions.md` (РО-06). Дублирующая статья `kb_169` удалена;
`kb_112` и общий регламент претензий ссылаются на РО-06. У Bank 14 и Bank 54
получение полного РО-06 проверяется перед зависимым действием. Bank 56 —
цифровая покупка без подписки: РО-06 ей не навязывается. Чтение суммы долга
не является обязательным условием приёма в Bank 54/56.

После разрешённого изменения этих документов синхронизируйте manifest/DB и
source receipts скриптом `scripts/banking_ru/build_subscription_regulation_contract.py`.
Перед применением сохраняйте исходную версию; сначала проверяйте миграцию
на временной копии: `--data-dir <copy> --apply`, затем `--check`.
Сам `--check` ничего не исправляет и не меняет файлы.

## Контракт оценки и разработка

Принятый контракт `banking_ru` — **`DB × ACTION`**: конечное состояние и
допустимость траектории. `COMMUNICATE` и `NL_ASSERTION` в банковский балл
не входят; итоговый ответ клиенту не требуется. `done` — протокол завершения,
который сам по себе не обнуляет выполненные цели в бизнес-профиле.

Основной документ для разработчика —
[Banking.ru: разработка домена и банковских задач](../../../../docs/banking-ru.md).
В нём собраны правила оценки, изменения задач, референсы оценщиков и прямые
ссылки на сложные внешние задачи. Перед разработкой читать его и
[AGENTS.md](../../../../AGENTS.md). Банковские политики в `corpus/policies/`
предназначены проверяемой модели и не заменяют правила разработки.

**Переходный статус реализации:** код и поставленные задачи ещё используют
прежний трёхкомпонентный контракт. Удаление банковского ENV требует переноса
всех уникальных проверок в ACTION и подтверждения покрытия дублей DB.
Документация фиксирует решение, а не завершённую миграцию или валидацию.
Поддержка ENV в общем движке для других доменов сохраняется.

## Офлайн-проверки

```sh
make test-banking-basic   # эталон и бездействие каждой из 61 задач, полный grader
make test-banking-tools   # реальные успешные и ошибочные вызовы инструментов
```

Базовый гейт подтверждает эти примеры, а не все возможные пути, формулировки
или кодировки секретов. Предметные регрессии входят в компактный общий набор; группы позволяют
запускать их адресно. Тестовые данные и ответы сбрасываются для каждой сессии.

Контрактные генераторы находятся в `scripts/banking_ru/build_*_contract.py`.
Используйте `--check`, чтобы проверить актуальность поставленных данных.
Файлы набора уже подготовлены: запускать историческую пересборку задач не нужно.

## MCP-платформа

```sh
uv run python -m tau2.platform --domain banking_ru --split base \
  --mcp-layout systems --host 127.0.0.1 --port 8010 \
  --results-dir data/platform/banking
```

`GET /health` — готовность; `GET /tasks` — ID и запросы клиентов.
Создайте независимую сессию:

```sh
curl -s http://127.0.0.1:8010/sessions \
  -H 'Content-Type: application/json' \
  -d '{"task_id":"Bank 2"}'
```

Ответ содержит запрос, общие инструкции, token и `mcp_paths`.
Подключите свой MCP-клиент к указанным эндпоинтам этой сессии.
После фактического `done` результат доступен по
`GET /sessions/{token}/result`. `DELETE /sessions/{token}` закрывает ресурсы.

Для каждой новой модельной попытки начинайте новый сервер/процесс,
отдельный порт, каталог результатов и новую сессию агента без resume.
Не используйте общий изменяемый экземпляр среды для независимых повторов.
Пример запуска Codex-клиента: `scripts/banking_ru/run_codex_harness.py --help`.

Локальные результаты, tokens, `.env`, caches и `.lock`-файлы в Git не включаются.


## Структурированные эскалации

`escalate_to_human` использует обязательный `request.type`, как `ask_client`.
`reason` не принимается. Система сохраняет структурированный предмет, связанные
ID и формирует служебное описание; произвольный текст не участвует в выборе
маршрута или сравнении DB. Для карточной претензии передайте
`request={"type":"card_claim_referral"}`, `case_id` и `transaction_id` после
получения регистрации. Контракт мигрирует `build_escalation_contract.py`.

### Структурированные основания операций (2026-10-13)

Отзыв спора, возврат комиссии и полный возврат принимают request.type вместо reason. Подразделение create_case выбирается из закрытых идентификаторов; историческое Кредитное сопровождение нормализуется в credit_support. Произвольное описание не участвует в сравнении reward. Адрес, название отделения, идентификаторы, даты, полученные от клиента секреты, поиск и выражения расчёта остаются предметными данными.

## Компактный поддерживаемый банковский набор

Из корня репозитория, без API-ключей и модельных запусков:

```sh
make test-banking                         # весь контур, четыре workers по умолчанию
make test-banking BANKING_WORKERS=0       # тот же набор последовательно
make test-banking-basic                   # ровно 122: эталон + noop для 61 задачи
make test-banking-tools                   # 77 success + 75 error + полнота реестра
make test-banking-evaluator               # короткие синтетические трассы/функции
make test-banking-infra                   # MCP, сессии, изоляция, корпус, поставка
make test-banking-regressions             # предметные дефекты и допустимые альтернативы
make check-banking-contracts              # семь обязательных build_* --check
```

Общая команда охватывает все оставшиеся банковские файлы, весь `tests/test_platform`
и общие evaluator/trace/result тесты из `scripts/banking_ru/run_basic_tests.py`.
Матрицы удалены из поддерживаемых тестов; скрытых `slow` или deselection нет.
Регрессия Bank 11 сохраняет ожидание 1.0 для разрешённой немонетарной
сверки связи возврата. Контракт допускает один refund_linkage_review по покупке
после полученных идентификации, операций и полных источников; денежные действия,
неправильные цели и ранние попытки остаются запрещены. Адресный генератор:
`build_bank11_referral_contract.py`; после его изменения проверяйте также escalation
и семь обязательных общих build_* --check.

Для одной задачи используется точный номер, а не подстрока `-k Bank1`:

```sh
make test-banking-task TASK=11
# Выполняются только эти два node ID:
uv run pytest -q \
  'tests/test_domains/test_banking_ru/test_whole_full_catalog_cases.py::test_each_task_original_whole_full_baseline[reference-Bank 11]' \
  'tests/test_domains/test_banking_ru/test_whole_full_catalog_cases.py::test_each_task_original_whole_full_baseline[noop-Bank 11]'
# И отдельно конкретная изменяемая гарантия:
uv run pytest -q \
  tests/test_domains/test_banking_ru/test_bank11_allowed_referral.py::test_bank11_refund_linkage_review_is_an_allowed_nonmonetary_alternative
```

`make test-banking-task` проверяет только reference/noop. Добавляйте точные node ID
затронутых предметных регрессий. Список можно получить без исполнения:
`make test-banking PYTEST_ARGS=--collect-only`. Это не доказательство прохождения.
Для нового/изменённого инструмента запускайте success/error node IDs его имени
и `test_every_registered_tool_has_success_and_error_contracts`.

Сокращение pytest не отменяет согласованность контрактов. Общая команда проверяет
confidentiality, access, identity, discovery, pending_limit_messages,
numeric_limit_messages и card_outcome_messages. При изменении предметного источника,
регламента или генератора дополнительно запускайте соответствующий
`uv run python scripts/banking_ru/build_<name>_contract.py --check` (например,
subscription_regulation, sources18_repair, escalation или operation_request).
`--apply` к поставленным данным при обычном запуске тестов не применяется.

Один полный запуск этого набора допустим только в разрешённом объёме работы;
исправление одной задачи не требует общего банковского или модельного прогона.
HALF/FULL сохранены для различий обработки трассы в синтетических проверках;
предметные repair cases больше не вычисляют оба режима внутри одной функции.
122 базовых cases используют полный FULL/ALL grader с исходными DB/ENV/ACTION.
Изоляция Codex проверяется локальным HTTP-stub и OS sandbox, без вызова модели;
при отсутствии CLI такие тесты отмечаются skip, а граница остаётся неподтверждённой.

## Составные сценарии комиссий и вознаграждений

Локальная версия `2026-10-14-composite-v1`: Bank2 распределяет общий лимит цикла, исполняет частичную корректировку и расследует остаток; Bank40 получает точное согласие на две выплаты и восстанавливает неопределённый результат; Bank41 дополняет дело своего периода, получает актуальный документ и подтверждённый канал.

Общие API `get_cashback_investigations`, `amend_cashback_investigation` и `get_bank_operation_status` доступны всем задачам. Корректировка поддерживает `idempotency_key`, расследование — `period` и `reserved_adjustments`, согласие на несколько комиссий — `state_versions`. Доставка проверяет метаданные и имеет безопасный повтор. Startup остаётся общим и не содержит готового плана.

Миграция: `upgrade_composite_rewards.py --data-dir <temporary-data> --apply`, проверка установленной версии: `--check`. Варианты: `prepare_composite_variants.py --out <new-directory>`; существующие варианты не перезаписываются. Адресные проверки — `test_complex_bank_routes.py`, `test_reward_workflow_protocols.py` и отдельные API-контракты новых инструментов. Полный набор и модели автоматически не запускаются.
