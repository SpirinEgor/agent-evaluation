# Banking.ru: банковский набор

Описание текущей поставки; сверено 27 октября 2026 года.

Набор содержит `Bank 1` … `Bank 61`, исходную БД, фиксированные ответы клиента,
общий корпус знаний и политики. У всех задач одна агентская среда и общий набор инструментов.
Меняются запрос клиента, предметное состояние, ответы и критерии оценки.

Это синтетический банк. Условия продуктов и операции заданы данными симуляции;
они не являются инструкцией по обслуживанию клиентов конкретного реального банка.

## Файлы задач

Каждая задача хранится отдельно: [`tasks/bank_001.json`](tasks/bank_001.json) …
[`tasks/bank_061.json`](tasks/bank_061.json). [`tasks.json`](tasks.json) — лёгкий
индекс `{"task_files": ["tasks/bank_001.json", …]}`; порядок списка задаёт порядок
набора. При копировании набора сохраняйте индекс вместе с папкой `tasks/`.
Для чтения и сохранения используйте `tau2.domains.banking_ru.task_store`:
`load_tasks`, `task_outputs` и `write_tasks`. Они также поддерживают прежний
массив задач для исторических снимков; сохранённые версии снимков не переписываются.

## Фиксированные ответы клиента

[`intake_answers.json`](intake_answers.json) — единственный канонический источник
ответов детерминированного клиента. Ответы сгруппированы по `customer_id`;
сценарная запись может содержать `task_id`, чтобы один клиент давал разные
ответы в разных задачах. Общие ответы идентификации доступны вместе с ответами
выбранного сценария. Это данные сценария, а не отдельная среда инструментов.

В канонической `db.json` нет копии `client_answers`, а `initial_state` задач
не подменяет ответы клиента. При создании среды загрузчик выбирает ответы из
intake и помещает их в рабочую БД сессии; изменения рабочей БД не меняют файл.
Ответ выбирается по структурированному `request` инструмента `ask_client`,
поэтому канонические записи не содержат `keywords` и неиспользуемых текстовых
ответов прежнего канала. Старые записи с `keywords` и прежние снимки остаются
читаемыми; закреплённые исторические fixtures сохраняют исходные байты.

## Корпус и manifest

Канонический `manifest.json` содержит ровно три SHA256: `corpus_sha256`,
`db_sha256` и `intake_answers_sha256`. Два последних проверяют исходные байты
`db.json` и `intake_answers.json`; хеш корпуса охватывает относительные пути
и байты всех файлов под `corpus/`, поэтому добавление, удаление и переименование
файла тоже меняют снимок. Список разрешённых документов в manifest не хранится:
доступные пути определяются обходом `corpus/` с проверкой границы каталога
и запретом символических ссылок.

Метаданные документа находятся в его YAML frontmatter. Для чтения служебного
представления используйте `tau2.domains.banking_ru.corpus_manifest.load_manifest`;
для подготовки согласованных изменений — `manifest_outputs`. Эти функции
поддерживают прежний manifest с `documents` в исторических снимках, сохраняя
его формат. Закреплённые файлы и хеши исторических fixtures не мигрируются.

## Установка после клонирования

Нужны Python 3.12 или 3.13, `uv` и `ripgrep` (`rg` в PATH).
Установите ripgrep средствами своей ОС, например `brew install ripgrep` на macOS
или `apt install ripgrep` на Debian/Ubuntu.

Из корня репозитория:

```sh
uv sync --frozen --extra dev --extra platform
make test-banking-package
```

Для офлайн-проверок API-ключи и установленный Codex не нужны.
Запуск самой модели требует её клиента и соответствующей авторизации.

Банковский набор пока не разделяется на выборки: загрузчик возвращает все задачи.
`split_tasks.json` и регистрация банковских сплитов удалены; разделение будет
определено отдельно.

## Единый регламент подписок

Процесс подписок, рекуррентных списаний и приёма связанной претензии находится
в `corpus/policies/subscriptions.md` (РО-06). Дублирующая статья `kb_169` удалена;
`kb_112` и общий регламент претензий ссылаются на РО-06. У Bank 14 и Bank 54
получение полного РО-06 проверяется перед зависимым действием. Bank 56 —
цифровая покупка без подписки: РО-06 ей не навязывается. Чтение суммы долга
не является обязательным условием приёма в Bank 54/56.

После разрешённого изменения документов сверяйте manifest, данные и source receipts.
Общий скрипт `scripts/banking_ru/sync_hardening_sources.py --data-dir <copy> --check`
проверяйте на временной копии; перед применением сохраните исходную версию и
проверьте полученные изменения критериев.

## Офлайн-проверки

Начинай с проверки выбранной задачи и изменённой гарантии:

```sh
make test-banking-task TASK=2
make check-banking-contracts
```

Первая команда — только эталон и бездействие Bank 2, не все её альтернативы.
Вторая выполняет четыре общих генератора в режиме `--check` без записи данных.
Остальные команды и границы выбора — в [процессе разработки](../../../../docs/banking-ru/development.md#как-выбирать-офлайн-проверки).
`make test-banking-basic` охватывает все задачи, а `make test-banking` — весь
явно поддерживаемый набор. Их не запускают автоматически после адресной правки.

Состав тестов задаёт `scripts/banking_ru/run_basic_tests.py`; новый файл
не добавляется в группы автоматически. Поддерживаемые fixtures самостоятельны
и не читают локальные снимки `artifacts/`. Успех базового набора не подтверждает
все возможные траектории и кодировки секретов. Сохранённые отчёты относятся
к своим версиям и не переписываются.

## MCP-платформа

```sh
uv run python -m tau2.platform --domain banking_ru --split base \
  --mcp-layout systems --host 127.0.0.1 --port 8010 \
  --results-dir data/platform/banking
```

`GET /health` — готовность; `GET /tasks` — ID и запросы клиентов.
Создайте независимую сессию:

```sh
curl -s http://127.0.0.1:8010/sessions \
  -H 'Content-Type: application/json' \
  -d '{"task_id":"Bank 2"}'
```

Ответ содержит запрос, общие инструкции, token и `mcp_paths`.
Подключите свой MCP-клиент к указанным эндпоинтам этой сессии.
После фактического `done` результат доступен по
`GET /sessions/{token}/result`. `DELETE /sessions/{token}` закрывает ресурсы.

Для каждой новой модельной попытки начинайте новый сервер/процесс,
отдельный порт, каталог результатов и новую сессию агента без resume.
Не используйте общий изменяемый экземпляр среды для независимых повторов.
Модельный harness требует preflight и подтверждённой контейнерной изоляции.
Подробный порядок и ограничения — в [разработке](../../../../docs/banking-ru/development.md).
Проверка `/health` здесь относится к сервису среды, а не доказывает готовность
или чистоту проверяемого агента.

Локальные результаты, tokens, `.env`, caches и банковские runtime `.lock`-файлы
в Git не включаются. Общий `uv.lock` версионируется.


## Структурированные эскалации

`escalate_to_human` использует обязательный `request.type`, как `ask_client`.
`reason` не принимается. Система сохраняет структурированный предмет, связанные
ID и формирует служебное описание; произвольный текст не участвует в выборе
маршрута или сравнении DB. Для карточной претензии передайте
`request={"type":"card_claim_referral"}`, `case_id` и `transaction_id` после
получения регистрации. Критерии эскалации записаны в задачах.

### Структурированные основания операций (2026-10-13)

Отзыв спора, возврат комиссии и полный возврат принимают request.type вместо reason. Подразделение create_case выбирается из закрытых идентификаторов; историческое Кредитное сопровождение нормализуется в credit_support. Произвольное описание не участвует в сравнении reward. Адрес, название отделения, идентификаторы, даты, полученные от клиента секреты, поиск и выражения расчёта остаются предметными данными.

## Исторический контекст составных сценариев

Локальная версия `2026-10-14-composite-v1`: Bank2 распределяет общий лимит цикла, исполняет частичную корректировку и расследует остаток; Bank40 получает точное согласие на две выплаты и восстанавливает неопределённый результат; Bank41 дополняет дело своего периода, получает актуальный документ и подтверждённый канал.

Общие API `get_cashback_investigations`, `amend_cashback_investigation` и `get_bank_operation_status` доступны всем задачам. Корректировка поддерживает `idempotency_key`, расследование — `period` и `reserved_adjustments`, согласие на несколько комиссий — `state_versions`. Доставка проверяет метаданные и имеет безопасный повтор. Startup остаётся общим и не содержит готового плана.

Исторические варианты описаны для контекста. Текущие задачи хранятся в `tasks/`; адресные проверки выполняются отдельно.
