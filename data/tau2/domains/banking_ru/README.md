# Banking.ru: 61 банковская задача

Набор содержит `Bank 1` … `Bank 61`, исходную БД, фиксированные ответы клиента,
общий корпус знаний и политики. У всех задач одна агентская среда и 65 инструментов.
Меняются запрос клиента, предметное состояние, ответы и критерии оценки.

Это синтетический банк. Условия продуктов и операции заданы данными симуляции;
они не являются инструкцией по обслуживанию клиентов конкретного реального банка.

## Установка после клонирования

Нужны Python 3.12 или 3.13, `uv` и `ripgrep` (`rg` в PATH).
Установите ripgrep средствами своей ОС, например `brew install ripgrep` на macOS
или `apt install ripgrep` на Debian/Ubuntu.

Из корня репозитория:

```sh
uv sync --frozen --extra dev --extra platform
make test-banking-package
```

Для офлайн-проверок API-ключи и установленный Codex не нужны.
Запуск самой модели требует её клиента и соответствующей авторизации.

## Единый регламент подписок

Процесс подписок, рекуррентных списаний и приёма связанной претензии находится
в `corpus/policies/subscriptions.md` (РО-06). Дублирующая статья `kb_169` удалена;
`kb_112` и общий регламент претензий ссылаются на РО-06. У Bank 14 и Bank 54
получение полного РО-06 проверяется перед зависимым действием. Bank 56 —
цифровая покупка без подписки: РО-06 ей не навязывается. Чтение суммы долга
не является обязательным условием приёма в Bank 54/56.

После разрешённого изменения этих документов синхронизируйте manifest/DB и
source receipts скриптом `scripts/banking_ru/build_subscription_regulation_contract.py`.
Перед применением сохраняйте исходную версию; сначала проверяйте миграцию
на временной копии: `--data-dir <copy> --apply`, затем `--check`.
Сам `--check` ничего не исправляет и не меняет файлы.

## Контракт оценки

Режим `completion_only`: агент получает результаты необходимых действий и вызывает
MCP-инструмент `done`. Итоговый ответ клиенту не требуется и не оценивается.
Структурированные вопросы для идентификации, уточнения и согласия остаются допустимыми.

Reward: `DB × ENV_ASSERTION × ACTION`. Проверяются состояние, владельцы,
авторизация, точные аргументы, ошибки/запрещённые попытки, полученные источники,
зависимости и порядок. Правильная итоговая БД не оправдывает раннее нарушение.
Бездействие и существенные ошибки дают 0. Допустимые альтернативы не обязаны
повторять формулировку эталона. Исходящие аргументы защищаются от утечек секретов.

## Офлайн-проверки

```sh
make test-banking-basic   # эталон и бездействие каждой из 61 задач, полный grader
make test-banking-tools   # реальные успешные и ошибочные вызовы инструментов
```

Базовый гейт подтверждает эти примеры, а не все возможные пути, формулировки
или кодировки секретов. Более подробные адресные проверки сохраняются отдельно
от базового набора. Тестовые данные и ответы сбрасываются для каждой сессии.

Контрактные генераторы находятся в `scripts/banking_ru/build_*_contract.py`.
Используйте `--check`, чтобы проверить актуальность поставленных данных.
Файлы набора уже подготовлены: запускать историческую пересборку задач не нужно.

## MCP-платформа

```sh
uv run python -m tau2.platform --domain banking_ru --split base \
  --mcp-layout systems --host 127.0.0.1 --port 8010 \
  --results-dir data/platform/banking
```

`GET /health` — готовность; `GET /tasks` — ID и запросы клиентов.
Создайте независимую сессию:

```sh
curl -s http://127.0.0.1:8010/sessions \
  -H 'Content-Type: application/json' \
  -d '{"task_id":"Bank 2"}'
```

Ответ содержит запрос, общие инструкции, token и `mcp_paths`.
Подключите свой MCP-клиент к указанным эндпоинтам этой сессии.
После фактического `done` результат доступен по
`GET /sessions/{token}/result`. `DELETE /sessions/{token}` закрывает ресурсы.

Для каждой новой модельной попытки начинайте новый сервер/процесс,
отдельный порт, каталог результатов и новую сессию агента без resume.
Не используйте общий изменяемый экземпляр среды для независимых повторов.
Пример запуска Codex-клиента: `scripts/banking_ru/run_codex_harness.py --help`.

Локальные результаты, tokens, `.env`, caches и `.lock`-файлы в Git не включаются.


## Структурированные эскалации

`escalate_to_human` использует обязательный `request.type`, как `ask_client`.
`reason` не принимается. Система сохраняет структурированный предмет, связанные
ID и формирует служебное описание; произвольный текст не участвует в выборе
маршрута или сравнении DB. Для карточной претензии передайте
`request={"type":"card_claim_referral"}`, `case_id` и `transaction_id` после
получения регистрации. Контракт мигрирует `build_escalation_contract.py`.

### Структурированные основания операций (2026-10-13)

Отзыв спора, возврат комиссии и полный возврат принимают request.type вместо reason. Подразделение create_case выбирается из закрытых идентификаторов; историческое Кредитное сопровождение нормализуется в credit_support. Произвольное описание не участвует в сравнении reward. Адрес, название отделения, идентификаторы, даты, полученные от клиента секреты, поиск и выражения расчёта остаются предметными данными.
